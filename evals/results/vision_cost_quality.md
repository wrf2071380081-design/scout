# 图片抽取：成本 vs 质量对照（云端 vs 本地，四条臂）

> ⚠️ **这份报告推翻了我自己两个事前判断**，值得完整读一遍。

## 实验设置

- 图片：`docker_containers.png`（**2086×466**，106 KB），Docker Desktop 容器列表截图
- ground truth：**18 项关键事实**（7 容器名 + 6 镜像名 + 5 端口），**客观可验证**
- 四条臂：

| 臂 | 工具 | 部署 | 成本模型 |
|---|---|---|---|
| A | kimi-k3（通用推理 VLM） | 云端网关 | 按 token 计费 |
| B | kimi-k3 + 降采样 1600px | 云端网关 | 按 token 计费 |
| C | **glm-ocr（专用 OCR，1.1B）** | **本机 Ollama** | **零（本地推理）** |
| D | glm-ocr + 降采样 1600px | 本机 Ollama | **零** |

## 结果

### 云端（kimi-k3，通用推理 VLM）

| 样本 | prompt | completion | 其中 reasoning | total | 命中 | 耗时 |
|---|---|---|---|---|---|---|
| A 原图 | 1417 | 2112 | 1,814（86%） | **3,529** | 18/18 | 66.7s |
| B 降采样 #1 | ~881 | ~11,341 | 11,041（90%） | **12,222** | 18/18 | 267.7s |
| B 降采样 #2 | 896 | 7,578 | 7,271（96%） | **8,474** | 18/18 | 228.5s |

### 本地（glm-ocr，专用 OCR，CPU）

| 样本 | prompt | completion | reasoning | total | 命中 | 耗时 |
|---|---|---|---|---|---|---|
| C 原图 | 1340 | 4096 | **0** | 5436 | 18/18 | **30.9s** |
| D 降采样 1600px | **806** | 4096 | **0** | 4902 | 18/18 | **25.0s** |

## 四个结论

### 1. 质量：**更正一个错误结论**（详见发现 ⓪）

初版指标只看单元格值，四条臂都是 18/18；把表头补进 ground truth（23 项）后，
**本地 glm-ocr 掉到 17/23**——它的表头是错的。详见下面「工程发现 ⓪」。

云端 kimi-k3 输出 **Markdown 表格**，本地 glm-ocr 输出 **HTML 表格**（`<table>`），
两者都忠实还原了原图内容，连被列宽截断的 `minio/minio:RELEASE.2024-05-28T1`
都一样——**读的是"屏幕上显示的"，这正是我们要的行为**。

### 2. 专用 OCR 不推理：reasoning 从 86~96% 降到 **0**

这是最干净的一条对比。同一张图：

- kimi-k3：**1,814 ~ 11,041** 个 reasoning token（OCR 根本不需要推理）
- glm-ocr：**0**

**OCR 是"看到什么写什么"，让它先思考是纯浪费。** 这条结论直接可讲。

### 3. 降采样的效果，两种工具**方向相反**

| | 云端 kimi-k3 | 本地 glm-ocr |
|---|---|---|
| prompt 变化 | 1417 → 896（−37%） | 1340 → 806（**−40%**） |
| **总成本/耗时变化** | **涨 2.4~3.5 倍**（推理波动淹没输入节省） | **耗时 −19%**（30.9s → 25.0s） |
| 结论 | **不划算，默认关闭** | **划算**，但收益温和 |

**原因**：云端是推理模型，总额由"想多久"主导（同图波动 6 倍）；
本地专用 OCR 没有推理开销，输入变小就近似线性地省下来。

→ 所以 `max_image_side` 对云端默认 `0`（关闭），对本地可以开。

### 4. 成本：本地是**零**

云端单张 3.5k~12k token；本地推理**不产生任何计费**。
代价是速度：本地 25~31s/张（CPU），云端 67~270s（含推理）。

## 五个工程发现（都是实测踩出来的）

### ⓪ **最重要的一个：我的评测指标有盲区，导致差点给出错误结论**

最初的 ground truth 只有 18 项，**全是"单元格里的值"**（容器名 / 镜像名 / 端口）。
结果四条臂都是 18/18，我据此写下"质量持平"。

**直到端到端验证时才发现不对**：把图片入库后检索能召回（4/4），
但**门控拒答了**（`coverage 0.31 < 0.5`）。深挖下去才看到根因——

| | 表头 |
|---|---|
| 原图真实值（英文） | `Name / Container ID / Image / Port(s) / CPU % / Last started` |
| **本地 glm-ocr（1.1B）** | `ID / Name / - / - / - / 0% / 3 months ago` ← **错**（把第一行数据当表头，还臆造了中文） |
| 云端 kimi-k3 | `Name / Container ID / Image / Port(s) / CPU % / Last started` ← **全对** |

**数据单元格两者都对，但表头只有大模型读得出。**

**为什么表头是决定性的，而不是装饰**：表头是**检索与门控的语义锚点**。
问"端口映射是什么"要靠 `Port(s)` 这个字面锚点才能匹配上；
表头错了/缺了，覆盖度就上不去，系统就**拒答一个它其实已经召回正确答案的问题**。

把表头补进 ground truth（18 → 23 项）后重测：
**本地 glm-ocr 17/23（74%），云端 kimi-k3 表头全对。**

→ **修正后的结论**：前面那句"四条臂都是 18/18、质量持平"**是错的**，
错在指标只看单元格。本地零成本路线**在表格类文档上质量不足**。

实际选型建议因此变成：

| 文档类型 | 建议 |
|---|---|
| 纯文字扫描件 | 本地 glm-ocr（零成本、25~31s） |
| **表格/复杂版式** | 云端大模型或更大的本地模型——**表头读不准会直接打穿检索** |

**这条教训比任何一条性能数字都值钱**：一个只检查"值"的指标，
会让所有模型看起来一样好，直到你在真实链路上发现系统在拒答。

### ① 端点的上下文上限会静默毁掉输出

Ollama 的 **OpenAI 兼容端点**在未显式指定上下文时，`prompt + completion` 被硬限在
**恰好 4096**。后果有两种，都很难发现：

- 输出在**表格中间被截断**（臂 C 初次实测：`postgres | 683` 就断了）
- 更隐蔽的：**撞上限后退化成复读**（表格写完后跟着 680 行 ```` ``` ````）
- 而**事实命中率仍然是 18/18**——因为它只检查关键词是否出现，
  不会发现"尾巴是垃圾"。

→ 改用 Ollama **原生** `/api/generate`（可用 `options.num_ctx` / `num_predict`），
并加**尾部退化裁剪**：从末尾往前找"同一行重复 ≥5 次"的连续段并裁掉。
判据只看尾部重复、不假设文档结构，所以"表格后面还有正文"的文档不会被误伤。

### ② 推理模型必须区分"没看到图"与"看到了但没输出"

`content` 为空时有两种情形，现象一样、修法完全不同：

| 现象 | 真实原因 | 修复 |
|---|---|---|
| 空 content + reasoning 里有答案 | 输出预算被推理吃光 | 调大 `max_tokens` |
| 空 content + reasoning 里没答案 | 模型没看到图 | 换模型 / 查 image_url 格式 |

**我本人就因此差点得出相反结论**：第一次探测 kimi-k3 时 `max_tokens=32` 被 29 个
推理 token 吃光，`content` 为空，我写下"它不支持图像"——直到 dump 原始 JSON
才看到 `reasoning_content` 里明明白白写着 "The image shows 7391"。

### ③ 网关会偶发 `finish_reason=content_filter`

同一张图、同样请求，第一次失败、再跑一次就成功 → **不是确定性拒绝**。
已给云端抽取器加**重试（默认 2 次）**。不重试会把偶发故障当成"这张图不能抽"，
进而**静默丢掉一篇文档**。

### ④ 响应字段名不能假设

GLM-OCR 官方文档只说"返回 Markdown 与 JSON 版面信息"，没给精确路径。
所以 MaaS 抽取器用候选键探测，**探不到就把真实顶层键名报出来**——
猜错字段名的表现是"抽取成功但内容为空"，而空内容会被上层当成
"这篇文档没内容"，最终静默丢数据。

### ⑤ 两种后端报用量的字段名不同

OpenAI 兼容用 `usage.prompt_tokens`，Ollama 原生用 `prompt_eval_count` / `eval_count`。
只读一种会让另一条路显示"用 0 token"——**而那个 0 会被误读成"免费"**。

## 复现

```bash
# 云端两臂（花钱）
set SCOUT_VISION_ENABLED=1 & set SCOUT_VLM_MODEL=kimi-k3
set VISION_ARMS=AB

# 本地两臂（免费）
ollama pull glm-ocr
set VISION_ARMS=CD

set VISION_TEST_IMAGE=<图片路径>
python scripts/vision_cost_quality.py
```
