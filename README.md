# scout

**一个能自证、能自愈、能自学的长文档 Agent。**

scout 不只是"能回答问题的 RAG"。它把三件事放进同一个运行时：

| 支柱 | 能力 | 对应问题 |
|---|---|---|
| **测量** | 四层评测（检索/生成/安全/轨迹）+ 16 类查询标签 + 模块级消融 | 「我怎么知道某个模块到底有没有用？」 |
| **恢复** | typed 失败分类 → 恢复动作表 → 预算与指纹抑制 | 「出错了怎么办？会不会死循环？」 |
| **学习** | 可选证据充分性门控、拒答校准、三层记忆与失效机制 | 「它知道什么时候该说不知道吗？」 |

```bash
git clone <this-repo> && cd scout
pip install -e ".[dev]"
scout demo          # 不联网、不需要 API Key，直接跑通一次 Agent 问答
scout eval run      # 在真实长文档语料上跑一次完整评测
scout eval ablation # 跑模块级消融，产出边际贡献对照表
```

> **零依赖起步**：仓库自带一个确定性离线实现（`HeuristicLLM` + 哈希向量器），
> 克隆下来立刻可跑。配置 `SCOUT_LLM_BASE_URL` 即可切到任意 OpenAI 兼容模型，
> 检索链路与评测代码一行都不用改。

## 它解决什么问题

长文档问答系统有一批**反复出现、又很少被认真对待**的失败模式：

1. **知识库为空和服务挂掉被混为一谈。** 把 Provider 异常吞成空结果，
   下游就把"服务挂了"渲染成"知识库里没有相关信息"，用户拿到一个自信的错误答案。
2. **经典 Auto-merging 会破坏排序。** 用父块替换命中的叶子块，
   等于把"因向量接近而被命中"的证据换成一个又长又泛的拼接块。
3. **查询改写的触发条件形同虚设。** 用"相关性低于阈值"触发，在真实语料上
   触发率常常是 0，模块挂着却从未执行。
4. **该拒答的时候最自信。** 给模型一段"看起来相关"的材料，
   它会倾向于从中拼出答案，而不是承认材料不够。
5. **Agent 会死循环。** 同一个工具、同一组参数被反复调用，
   把一次请求放大成十几次外部调用。
6. **评测只测"答案对不对"。** 检索准不准、过程是否浪费、该拒有没有拒——
   这些维度没有指标，于是系统坏在哪一层永远说不清。

scout 针对上面每一条都有对应的机制和**可测量的验证**。

## 三个关键设计决定

### 一、Auto-merge 默认"只附加上下文"，而不是替换

经典 Auto-merging 的逻辑是：同一父块下命中 N 个以上叶子块，就把它们整体换成父块。
直觉合理，但代价被忽视了——**替换会破坏排序**。叶子块之所以被命中，
是因为它的向量与查询最接近；父块是多个叶子块的拼接，向量被稀释、长度大一个数量级。

scout 提供两种模式，并且把差异做成可测量的：

| 模式 | 检索身份 | 上下文 | 后果 |
|---|---|---|---|
| `REPLACE` | 换成父块 | 父块全文 | 排序信号被稀释 |
| `EXPAND`（默认） | **仍是叶子块** | 附加父块全文 | 精度与上下文完整性同时保留 |

```python
auto_merge(units, catalog, mode=MergeMode.EXPAND, threshold=2)
```

两种模式都可以一键切换参与消融，由实验而不是直觉来裁决。

### 二、查询改写由"缺陷诊断"触发，而不是"相关性阈值"

阈值触发有个致命缺陷：**它无法回答"改写什么"**。相关性低有很多种原因——
错别字、术语不匹配、问得太窄、问得太泛——需要完全不同的改写方向。
而且阈值在真实语料上常常永远不满足，模块挂着却从不执行。

scout 换一个判据：先诊断查询自身的缺陷，再由缺陷决定方向。

| 缺陷 | 判据 | 改写方式 |
|---|---|---|
| `TYPO` | 查询词不在语料词表，但存在编辑距离 ≤1 的语料词 | 词项替换（**不调模型**） |
| `ALIAS` | 不在词表的词占比过高（术语体系不匹配） | HyDE 假设性文档 |
| `TOO_NARROW` | 大量低文档频率的具体词（型号/编号/长实体） | Step-back 退步 |
| `TOO_BROAD` | 查询极短且全是高频泛词 | 补限定 / 请澄清 |

触发条件本身可测：构造必然需要改写的难例集，改写触发率就是一个真实数字，
而不是一个永远为 0 的装饰。

### 三、证据充分性用"双维度"判定

只用加权覆盖率会漏掉一类致命情况：政策语料里 "建设""标准" 几乎每篇都出现，
而 "火星""殖民" 一次都没有。问题「火星殖民基地的建设标准是什么」的覆盖率
会被前半段撑到 0.58，从而绕过拒答门控。

原因是覆盖率把所有词一视同仁。所以引入第二个维度：

- `coverage`：全部实义词的 **IDF 加权**覆盖 → 材料整体对不对题
- `focus_coverage`：多字词/拉丁词等**具体概念词**的未加权覆盖 → 问题真正在问的东西找到了吗

两者必须同时达标。`focus_coverage` 刻意不加权，因为加权会让跨词边界的
伪双字组（"建**设标**准"切出的 `设标`，df=1 因而 IDF 极高）主导分子，反而放大噪声。

## 评测框架

四层指标，**一共 23 项**，其中轨迹层与拒答校准是大多数项目缺失的部分：

**检索层** `Recall@1/3/5/10`、`MRR`、`nDCG@10`、`目标来源命中率`
**生成层** `关键词覆盖率`、`归因支撑率`、`证据覆盖率`、`拒答正确率`、`幻觉率`、`误拒率`
**安全层** `注入泄漏率`
**轨迹层** `平均步数`、`工具调用数`、`工具失败率`、`重复调用率`、`预算终止率`
**性能层** `P50/P95 延迟`、`token 消耗`

配套三份产物：

- **单次报告**：分层指标 + 标签切片（定位是哪一类查询坏了）+ 问题样本清单
- **消融对照表**：每个模块的边际贡献，**含负贡献**
- **失败分类学**：失败按错误码 / 阶段 / 恢复动作的分布

数据集设计上有一个决定值得说明：**gold 用文本片段而不是 chunk_id**。
chunk_id 依赖分块参数，把叶子块从 800 字符改成 600 就会让整个标注集作废；
而"这段文字应当被检索到"与分块策略解耦。代价是判定稍慢，
换来的是**标注集能在分块消融中反复复用**。

## 实测结果（含负向结论）

语料：`datasets/longdoc-gold/`，40 篇公开长文档（20 篇 A 股年报摘要 + 20 篇政策/标准），
切分后 **988 个叶子块**。标注集：`evals/longdoc_v1.json`，19 条样本覆盖 14 类标签。

> ⚠️ **样本量很小（19 条），以下数字只具方向性，不构成统计结论。**
> 扩大标注集是本项目下一步的首要工作。

### 拒答校准：一次真实的过校正（含负向结论）

在自有语料上做拒答门控迭代，得到了一组比"一次改好"更有意思的数据：

| 方案 | 拒答正确率 | 幻觉率 | 误拒率 | 作答率 |
|---|---|---|---|---|
| 朴素覆盖率 | **0%** | 100% | 0% | 100% |
| 只做 IDF 加权 | 100% | 0% | **90%** | 5% |
| IDF + 焦点词双门控 | 50% | 50% | 0% | 84% |
| 再修分词器缺陷 | **100%** | **0%** | **0%** | 68% |

过程里的三个发现：

1. **IDF 加权把门控从"从不拒答"直接推成"几乎全拒"。** 说明问题不在权重函数，
   而在阈值没有随尺度重新校准——换权重函数必须重标阈值。
2. **调参过程中暴露了一个真 bug。** 首次 IDF 加权后出现了 `coverage = -83.86`
   这种荒谬值，根因是 `document_frequency` 按 **chunk** 统计（df 最大 898）
   而 `corpus_size` 传的是**文档数**（40），df > N 使 IDF 变负。
   修法是统一口径，并让 IDF 函数对越界输入夹到正数下界而不是返回负值。
3. **最终把两头拉正的是分词器修复。** 原实现在全文所有相邻汉字上生成双字组，
   不管空格与标点，于是"单线**程 内**存"被切出伪双字组 `程内`。
   这类伪词在语料里几乎不存在因而 IDF 极高，污染了排序与覆盖率估计，
   还曾把"错别字纠正"误触发到正常查询上。改成**只在连续中文段内**生成双字组后，
   拒答正确率与误拒率同时达到最优，检索指标也跟着提升。

详细的排查过程见 [`docs/FINDINGS.md`](docs/FINDINGS.md)。

### 检索与生成

| 指标 | 值 |
|---|---|
| Recall@1 / @3 / @5 | 78.9% / 84.2% / 84.2% |
| MRR / nDCG@10 | 70.2% / 70.8% |
| 目标来源命中率 | 100%（17 例） |
| 归因支撑率 | 100%（13 例） |
| 注入泄漏率 | 0%（1 例） |
| P95 延迟 | 84 ms（40 篇语料 / 988 块 / 离线实现） |

### 消融实验：每个模块的边际贡献

19 条样本 × 8 种配置，在**同一份共享索引**上各跑一遍：

| 配置 | 改动 | Recall@5 | MRR | ΔMRR |
|---|---|---|---|---|
| 全量基线 | — | 94.7% | 68.6% | — |
| 仅稠密（关掉其余一切） | − | 68.4% | 26.7% | **−41.9pp** |
| 关掉重排 | − | 78.9% | 52.4% | **−16.2pp** |
| 关掉复杂度路由 | − | 94.7% | 71.2% | +2.6pp |
| 关掉查询改写 | − | 89.5% | 67.5% | −1.1pp |
| 关掉父块合并 | − | 94.7% | 68.6% | 0.0pp |
| 换成 REPLACE 合并 | 切换 | 94.7% | 75.4% | **+6.8pp** |
| 关掉充分性门控 + 注入防护 | − | 94.7% | 68.6% | 0.0pp |

四条真结论：

1. **混合检索是最大的杠杆。** 只用稠密向量，MRR 掉 41.9pp——高于其他任何单一模块。
2. **重排贡献第二**（+16.2pp）。改写在 19 条样本上反而是轻微负贡献（−1.1pp），
   这在真实系统里也常见——误导性的改写比不改更糟糕。
3. **Auto-merge 的行为比主流说法复杂得多。**

   "REPLACE 用父块替换叶子块会稀释排序"，是我在 SuperMew 那个长文档项目上的实测结论
   （裸检索 MRR 1.000 → 完整流水线 0.857，当时是归因到它的）。

   把同一份 **EXPAND 默认** 的实现搬到这份语料上，
   **REPLACE 反而比 EXPAND 高 6.8pp，而 EXPAND 与"关掉合并"打平**。

   两条数据拼到一起才能看清真实的结论：**Auto-merge 的效果方向随语料与重排器而变动**，
   不该靠直觉决定，要靠各自的消融实验。这也是本项目把每个模块都做成可开关的原因。
   另外，本轮消融顺手还发现一个实现缺陷（重排器拿父块全文去打分会让 EXPAND 被自己稀释），
   修复方式是**重排只认叶子块的身份文本**——细节见 [`docs/FINDINGS.md`](docs/FINDINGS.md)。
4. **关掉门控不影响检索指标。** 充分性门控只改变"答案是否放行"，不改变检索阶段，
   说明它不会拖累召回——这正是守门员该做的事。

完整对照表带差量列，见 `reports/ablation/ablation.md`（每次运行都会重生成）。

标签切片能直接指出短板：**跨文档类 Recall@5 仅 33%**、
**多对象对比类 0%**——单路 Top-K 在需要同时取到两份文档时不成立，
这正好指向"子问题分解 + 多路召回合并"的改进方向。

## 已知限制

诚实列出，避免读者高估：

1. **标注集只有 19 条**，覆盖 14/16 类标签。`source_conflict` 与 `code`
   两类因当前语料不含冲突来源与代码文档而**故意留空**——编造一条不是冲突的"冲突样本"
   会让这个标签失去意义。
2. **离线实现的答案质量有限。** `HeuristicLLM` 用词法抽取拼答案，
   会出现"从电商文档里摘出含 Redis 的句子"这类偏差。
   它的定位是让流程**可复现**，不是**能打**。生产请配置真实模型。
3. **哈希向量器是词法信号，不是语义向量。** 它的检索质量显著低于 BGE 等模型，
   但保证了"克隆即可跑"。换向量器只需替换一个类。
4. **索引是单机内存实现**，重排器是词法占位实现。生产应换成向量数据库
   与跨编码器，接口形状不变。
5. **充分性判定仍会漏判**（见上文 50%）。纯词法手段难以可靠区分
   "主题词重叠"与"真的能回答"，根治需要模型侧判断。
6. **轨迹学习（trace → 偏好对 → DPO）尚未实现**，目前只有 trace 采集与失败分类。

## 配置

所有参数走环境变量，全部有安全默认值。常用项：

```bash
# 切换到真实模型（不配置则使用离线确定性实现）
export SCOUT_LLM_BASE_URL="https://api.openai.com/v1"
export SCOUT_LLM_API_KEY="sk-..."
export SCOUT_LLM_MODEL="gpt-4o-mini"

# Agent 预算
export SCOUT_AGENT_MAX_STEPS=8
export SCOUT_AGENT_MAX_TOOL_CALLS=12
export SCOUT_AGENT_DEADLINE_SECONDS=120

# 检索
export SCOUT_RETRIEVAL_TOP_K=8
export SCOUT_RRF_K=60
export SCOUT_AUTO_MERGE_ENABLED=true

# 拒答门控（两个阈值必须同时满足）
export SCOUT_SUFFICIENCY_MIN_COVERAGE=0.5
export SCOUT_SUFFICIENCY_MIN_FOCUS_COVERAGE=0.5
```

`scout info` 会打印当前生效的全部配置。
