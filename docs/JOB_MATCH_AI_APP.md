## 二、必须补的四项

### 补 1：scout 改成 RAG 口径（零成本，优先级最高）

现在的问题：**通篇读不出"我做过知识库问答"**。改动只有三处：

1. 项目名 / 首句直接写 **「RAG 知识库问答系统」**
2. 数据层那句加"**文档解析 → 分块 → 向量化 → 混合检索 → 重排 → 生成的完整 RAG 链路**"
3. 把**长文档中文语料**那组数字前置（那才是"知识库问答"场景），MuSiQue 多跳作为补充

### 补 2：加一条 Prompt Engineering（零成本，代码里全都有）

代码里真实存在、简历里完全没有的东西：

| 文件 | 内容 |
|---|---|
| `COMPLEXITY_PROMPT` | 判据式分类：给出"简单/复杂"的判定标准，强制 JSON 输出 |
| `SUBQUESTION_PROMPT` | 复杂问题拆 2~4 个独立子问题，显式约束"避免互相包含" |
| `GRADE_PROMPT` | 四维评分（相关性/覆盖度/可答性/歧义）+ 四路路由（作答/改写/澄清/无知识） |
| `ANSWER_PROMPT` | 强制引证编号 `[1]`、证据不足必须明说、禁止推测、不引用编号外内容 |
| `AGENT_SYSTEM_PROMPT` | ReAct 工具使用规范 + 防重复调用 |
| 严格模式重生成 | 校验发现无支撑结论时，**在提示词前缀注入具体失败原因后重生成** |
| 裁判 prompt | 评分 rubric + pairwise，含位置偏见去偏（双跑换序） |

**建议写法**（能力清单体，不解释）：

> **Prompt 工程与输出约束**：设计 7 类任务提示词（复杂度路由 / 子问题分解 / 证据充分性评分 / 引证式生成 / ReAct 工具规范 / 查询改写 / 评分 rubric），全部以 Pydantic Schema 强制 JSON 结构化输出；生成侧强制来源编号引证与"证据不足即拒答"；建立**失败驱动的提示词迭代**——归因校验发现无支撑结论时，把具体失败原因注入提示词前缀触发重生成。

### 补 3：多模态 —— ✅ 已完成（代码 + 写法）

**方案 A（已做）**：把实习经历里的图像能力显式化。原文写的是"解决工业产品缺陷的自动化检测与分割问题"——**这本身就是图像理解**。改为：

> 禾思 Omega 平台：**基于深度学习的工业视觉质检平台**，覆盖图像数据上传、标注、多框架模型训练与推理，实现工业产品**缺陷检测与语义分割**（**计算机视觉 / 图像理解**方向）；负责训练管理、标注管理与平台基础能力三个核心模块。

技能栏加一行：**计算机视觉（目标检测 / 语义分割 / 轮廓提取）**。

**方案 B（已做，代码）**：给 scout 加了**图片/扫描件入库入口**，走同一条流水线：

- `data/extract.py`：`TextExtractor` 协议 + `VLMTextExtractor`（OpenAI 兼容视觉消息 +
  base64 data URL）+ `PlainTextExtractor` + `StubTextExtractor`（离线替身）。
- 抽取后的文本直接进 `ingest()` —— **复用版面还原 / 切分 / 去重 / 版本，一行没改**。
- 关键设计：**没配视觉模型就拒绝**（把图片发给纯文本模型不会报错，只会自信胡编）；
  抽取结果带"未经人工校验"警告；空结果必须报警（否则表现为"入库成功但什么都没进"）。
- CLI：`scout ingest --images`。

**为什么不选传统 OCR（tesseract）**：① 要装二进制依赖，破坏"克隆即可离线跑"；
② **传统 OCR 只输出字符流、保不住版面**——表格会被拉平，而这恰好是数据层最需要保住的东西。
VLM 可直接输出 Markdown 表格，**版面在抽取阶段就被保住**。代价是成本与幻觉风险，所以边界写清：
图片抽取结果默认只进"待复核区"。

### 补 4：向量数据库 —— ✅ 已完成（Milvus，不是 FAISS）

原来建议用 FAISS（因为 Milvus 要起 etcd + MinIO）。**但你本地 Docker 里已经有整套 Milvus 栈**
（`milvus-standalone` 2.5.14 + `milvus-etcd` + `milvus-minio`，19530 已映射），
所以直接用 Milvus——**岗位原话里就点了它，比 FAISS 更贴**。

实现（`src/scout/rag/milvus_store.py`）：

- `MilvusDenseStore`：建集合 / 写入 / 检索 / 报状态，**只做稠密通道**，不碰融合与重排。
- `MilvusHybridIndex`：**只覆写 `_dense_ranked` 一个方法**，BM25、RRF、候选池、
  合并逻辑全部继承——这正是 `index.py` 里那句承诺的字面兑现
  （*"生产环境应把 search() 换成向量数据库……接口形状保持不变"*）。
- **集合名由「前缀 + 语料指纹 + 向量器身份」派生**：换语料或换向量器就是换集合。
  复用集合不会报错，只会返回"属于旧语料/旧语义空间"的结果——最难排查的一类脏数据事故。
- **不可达时显式降级**（写进 `SearchResult.degraded_code`），`strict=True` 时**拒绝降级**——
  出评测报告时必须用 strict，否则指标可能来自内存兜底而报告上看不出来。
- **两种后端由同一个入口构造**（`build_index(milvus=...)`），
  所以"换后端前后指标是否一致"是可以验证的，而不是一句声称。

**联机冒烟**：`scout milvus-smoke` 会输出连通性 + 两种后端 top-k 重合度 + 延迟对照。
**重合度就是 HNSW 的近似召回损失**（内存是精确暴力，Milvus/HNSW 是近似）——
这个数字回答"为了这个延迟，我们付出了几个百分点的召回"。

⚠️ **现状**：容器目前是**停止**状态（19530 端口未监听）。
先跑 `docker start milvus-etcd milvus-minio milvus-standalone`（standalone 依赖 etcd 与 MinIO，缺一不可），
再执行 `scout milvus-smoke` 就能拿到联机报告。**代码与离线测试已全部就绪，只差容器。**
