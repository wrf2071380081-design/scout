## 二、必须补的四项

### 补 1：scout 改成 RAG 口径（零成本，优先级最高）

现在的问题：**通篇读不出"我做过知识库问答"**。改动只有三处：

1. 项目名 / 首句直接写 **「RAG 知识库问答系统」**
2. 数据层那句加"**文档解析 → 分块 → 向量化 → 混合检索 → 重排 → 生成的完整 RAG 链路**"
3. 把**长文档中文语料**那组数字前置（那才是"知识库问答"场景），MuSiQue 多跳作为补充

### 补 2：加一条 Prompt Engineering（零成本，代码里全都有）

代码里真实存在、简历里完全没有的东西：

| 文件 | 内容 |
|---|---|
| `COMPLEXITY_PROMPT` | 判据式分类：给出"简单/复杂"的判定标准，强制 JSON 输出 |
| `SUBQUESTION_PROMPT` | 复杂问题拆 2~4 个独立子问题，显式约束"避免互相包含" |
| `GRADE_PROMPT` | 四维评分（相关性/覆盖度/可答性/歧义）+ 四路路由（作答/改写/澄清/无知识） |
| `ANSWER_PROMPT` | 强制引证编号 `[1]`、证据不足必须明说、禁止推测、不引用编号外内容 |
| `AGENT_SYSTEM_PROMPT` | ReAct 工具使用规范 + 防重复调用 |
| 严格模式重生成 | 校验发现无支撑结论时，**在提示词前缀注入具体失败原因后重生成** |
| 裁判 prompt | 评分 rubric + pairwise，含位置偏见去偏（双跑换序） |

**建议写法**（能力清单体，不解释）：

> **Prompt 工程与输出约束**：设计 7 类任务提示词（复杂度路由 / 子问题分解 / 证据充分性评分 / 引证式生成 / ReAct 工具规范 / 查询改写 / 评分 rubric），全部以 Pydantic Schema 强制 JSON 结构化输出；生成侧强制来源编号引证与"证据不足即拒答"；建立**失败驱动的提示词迭代**——归因校验发现无支撑结论时，把具体失败原因注入提示词前缀触发重生成。

### 补 3：多模态——先改写法，再考虑补项目（两档方案）

**方案 A（低成本，30 分钟）**：把实习经历里的图像能力显式化。现在写的是"解决工业产品缺陷的自动化检测与分割问题"——**这本身就是图像理解**。改成：

> 禾思 Omega 平台：**基于深度学习的工业视觉质检平台**，覆盖图像数据上传、标注、多框架模型训练与推理，实现工业产品**缺陷检测与语义分割**（**计算机视觉 / 图像理解**方向）；负责训练管理、标注管理与平台基础能力三个核心模块。

再加一行技能栏：**计算机视觉（目标检测 / 语义分割 / 轮廓提取）**。

**方案 B（更贴岗位，1~2 小时）**：给 scout 加真正的多模态入口。岗位要的是"多模态能力**集成**"（接 ASR/OCR/VLM API），而 scout 现在的入库是纯文本。最直接的补法：

- 在数据层加「**扫描件 / 图片 → OCR 或 VLM 抽取 → 走同一套入库流水线**」
- 收益：一句话就能写"支持扫描件与图表的多模态入库"，且**与现有双栏/跨页表格解析是同一层能力，叙事连贯**
- 成本：接一个 OCR/VLM 接口（几十行）+ 一个可离线复现的 stub

**我的建议**：A 立刻做，B 看时间。**A 是"把已有的说清楚"，B 是"补新能力"**——前者不能省，后者是加分。

### 补 4：向量数据库（唯一需要写代码的硬缺口）

岗位明确点了 Milvus / FAISS / Weaviate，你一个都没有。但**这个缺口最好补，因为脚手架已经在了**：

`src/scout/rag/index.py` 的 docstring 原文：

> 这是单机内存实现，目的是让评测与消融可以完全离线复现。
> 生产环境应把 `search()` 换成向量数据库（Milvus / Qdrant / pgvector）
> 的原生混合检索；**接口形状保持不变，上层流水线与评测代码无需改动**。

也就是说：**加一个 FAISS 后端 = 实现同一个 `search()` 接口 + 保持所有评测可复现**。
预计 1~2 小时，用 `faiss-cpu`（pip 装、离线可用、无需服务）。

补完之后可以诚实写：

> **向量索引后端**：抽象统一检索接口，实现内存索引与 **FAISS（HNSW/IVF）** 两种后端，
> 支持稠密 + BM25 混合召回与 RRF 融合；**同一套评测可在两种后端上复现**，
> 以对比召回率与延迟。

**为什么不选 Milvus**：Milvus 要起服务（etcd + MinIO），在"离线可复现"这个约束下是负收益。
FAISS 是纯库，且岗位原话里就列了它。**面试被问"为什么不用 Milvus"时，答案是"我们的评测要求离线单机可复现，FAISS 满足；生产要多租户和水平扩展时再换 Milvus，接口已经抽象好了"**——这个回答比"我用过 Milvus"更有说服力。

## 四、建议谨慎处理的三处

1. **通义 / 文心 / Llama**：你的协议适配是 OpenAI / Anthropic / Gemini / Responses，**不含这三家**。
   要么真接一个（通义兼容 OpenAI 协议，改个 base_url 加个模型名，10 分钟），要么别写。
   **不要凭"我用过"写上去**——面试官问"文心的 function calling 格式和 OpenAI 有什么差别"就穿。
2. **"多模态"这个词**：A 方案把它锚在"图像理解 / 计算机视觉"上是诚实的；
   但不要说成"多模态大模型应用"，那是另一件事。
3. **对话系统**：scout 有澄清与审批交互，可以写"多轮澄清"，
   但不要写成"对话系统开发经验"——你没有会话管理与多轮上下文的实现。
