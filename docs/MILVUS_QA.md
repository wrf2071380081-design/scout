## 一、架构与组件

### Q1：Milvus 有哪些组件？standalone 和 cluster 差在哪？

**答案**：Milvus 是**存算分离 + 组件化**架构，四个角色（2.3 之后统一为 4 个 coordinator）：

| 角色 | 职责 |
|---|---|
| **Proxy** | 无状态接入层，客户端只连它；做请求路由与结果聚合 |
| **Coordinator**（root/data/query/index） | 无状态管理节点：root 管 DDL/TSO，data 管写入与刷盘，query 管查询调度，index 管索引构建 |
| **Worker**（data node / query node / index node） | 有状态/计算节点：query node 持有 segment 提供检索，index node 建索引，data node 消费日志写存储 |
| **依赖存储** | **etcd**（元数据与选主）、**对象存储 MinIO/S3**（向量与日志数据）、**消息队列 Pulsar/Kafka**（WAL，2.3+ 可配 RocksMQ） |

**standalone 就是把这四类角色塞进一个进程**，依赖仍然需要 etcd + MinIO + MQ。
所以"standalone 起不来"通常是依赖没起来——**我这次就踩了**：
`milvus-standalone` 依赖 `milvus-etcd` 与 `milvus-minio`，三者必须都在。

**追问：为什么非要 etcd 和 MinIO？**
etcd 提供**分布式协调与强一致元数据**（集合 schema、segment 状态、TSO 时间戳）；
MinIO 存**真正的向量数据与 binlog**，让计算节点无状态化、可水平扩容。
这两个是"存算分离"的代价：换来的是 query node 可以随意扩缩容而数据不丢。

**我们项目的实际**：
```
milvus-standalone  milvusdb/milvus:v2.5.14   →  19530 (SDK) / 9091 (metrics)
milvus-etcd        coreos/etcd:v3.5.18
milvus-minio       minio/minio:RELEASE.2024-05-28
```
启动顺序有依赖：`docker start milvus-etcd milvus-minio milvus-standalone`，缺一个连不上。

## 二、索引类型与选型

### Q2：Milvus 有哪些索引？怎么选？

| 索引 | 类型 | 特点 | 适用 |
|---|---|---|---|
| **FLAT** | 暴力 | 100% 召回，无压缩，慢 | 小数据集（<10万）、召回基线 |
| **IVF_FLAT** | 量化倒排 | 聚类成 nlist 个桶，查 nprobe 个桶 | 召回/速度平衡，最常用 |
| **IVF_SQ8** | 标量量化 | 每维 float32→int8，内存降到 1/4 | 内存受限，接受少量精度损失 |
| **IVF_PQ** | 乘积量化 | 分维成子空间各自量化，压缩最狠 | 超大规模、内存极敏感 |
| **HNSW** | 图 | 分层可导航小世界图，查询最快、召回高 | **低延迟优先，最主流** |
| **DISKANN** | 磁盘图 | 图存磁盘，省内存 | 十亿级、内存放不下 |
| **SCANN** | 量化 | Google 的方案，只支持部分 metric | 特定场景 |
| **GPU_*** | GPU | CAGRA/GPU_IVF 等 | 吞吐敏感、有 GPU |

**一句话选型**：小数据 FLAT；要低延迟 HNSW；要省内存 IVF_PQ / DISKANN；
GPU 上 CAGRA。**没有"最好"的索引，只有匹配数据规模与延迟预算的索引。**

### Q3：HNSW 的原理和参数？

**原理**：把向量组织成**多层图**，底层含全部点，上层是稀疏"高速公路"。
查询从顶层贪心下降，每层在候选里找最近的，到底层做精细搜索。
复杂度从 O(n) 降到约 O(log n)。

**三个参数（必须能说清各自影响什么）**：

| 参数 | 位置 | 调大的效果 | 代价 |
|---|---|---|---|
| `M` | 建索引 | 每个节点的最大连接数↑，召回↑ | 内存与建索引时间↑ |
| `efConstruction` | 建索引 | 建图时搜索宽度↑，图质量↑ | 建索引变慢 |
| `ef` | **查询时** | 搜索宽度↑，召回↑ | **延迟↑**（唯一一个运行时可调的） |

**追问：`efConstruction` 和 `ef` 的关系？**
`efConstruction` 决定**图建得好不好**（一次性成本），`ef` 决定**这次查得多细**（每次成本）。
`ef` 必须 ≥ top_k，一般取 `top_k × 2~10`。**调优顺序：先固定 M/efConstruction 建好图，
再在线调 ef 找延迟与召回的平衡点。**

**我们项目的实际**：
```python
# HNSW(M=16, efConstruction=200)，查询 ef = max(64, top_k × 4)
search_params = {"params": {"ef": max(64, limit * 4)}}
```
选 HNSW 的理由：**低延迟优先**（在线问答，用户等不起），且我们的数据量在万级，HNSW 内存占用完全可以接受。

### Q4：IVF 的 nlist / nprobe 是什么？

`nlist`＝把向量聚成多少个簇（建索引时），`nprobe`＝查询时扫几个簇。
`nprobe/nlist` 越大召回越高、越慢。经验：`nlist ≈ 4 × sqrt(N)`，`nprobe` 从 1 开始调到召回达标。
**IVF 的核心风险是"边界效应"**：真答案落在没被扫的簇里，召回直接归零——
所以 IVF 的召回曲线通常比 HNSW 更"脆"。

## 三、一致性（高频追问区）

### Q5：Milvus 的一致性级别？为什么写入后要 flush？

四个级别：

| 级别 | 含义 |
|---|---|
| **Strong** | 读到最新已提交数据（要等 TSO 推进，最慢） |
| **Bounded**（默认） | 容忍有界延迟（默认 5s）内的不一致，**性能与正确性的折中** |
| **Eventually** | 只保证最终一致，最快 |
| **Session** | 保证**本客户端**自己的写能被自己读到 |

**flush 的作用**：Milvus 写入先进**消息队列（WAL）**，data node 消费后落到对象存储成为
**sealed segment** 才能被索引与检索。`flush()` 强制把已写入的数据封段并触发建索引。

**追问：不 flush 会怎样？**
表现为**间歇性"刚写进去搜不到"**——数据还在 growing segment（内存里、未建索引）。
这是最烦的一类 bug：单次测试通过、压测时偶发失败、重试又好。

**我们项目的实际**：
```python
client.insert(collection_name=name, data=[...])
client.flush(name)   # 让刚写入的数据立刻可检索
```
注释里我写明了理由：*"不 flush 会出现'刚同步完却搜不到'的间歇性失败，最难排查"*。
另外同步策略选的是**全量重建（drop + create + insert）而不是增量 upsert**——
因为评测要的是**幂等**：同一份语料跑两次必须得到完全一样的集合状态。
增量 upsert 在删除场景会残留**孤儿向量**，而孤儿向量会污染召回。

## 四、检索与过滤

### Q6：Milvus 怎么做标量过滤 + 向量检索？

两种执行顺序，**区别很关键**：

- **pre-filter**：先按标量条件筛出候选集，再在候选集里做向量检索。
- **post-filter**：先向量检索 top-k，再用标量条件过滤 → **可能过滤后剩不下几条**（top-k 被过滤光）。

Milvus 会按**过滤条件的选择率**自动选择：选择率高（滤掉很多）时倾向 pre-filter。
实践中如果你发现"加了过滤条件后结果变少"，先怀疑 post-filter 吃掉了结果——
解决方式是**放大 top-k** 或改用支持 pre-filter 的索引/参数。

### Q7：稠密 + 稀疏混合检索在 Milvus 里怎么做？

Milvus 2.4+ 支持**多向量字段**（一个 collection 里同时有 dense 与 sparse 字段），
可以用 **RRF（Reciprocal Rank Fusion）** 或加权求和做混合检索，**服务端一次完成**。

**我们项目的实际（诚实的对比）**：
我们用 Milvus **只做稠密通道**，稀疏（BM25）与 RRF 融合仍在 Python 侧。
理由是**评测可复现性**：BM25+RRF 在本地算，不受服务端版本差异影响，
离线/在线两条路径的融合逻辑**完全同一份代码**。
这是一次明确的取舍——把"分布式混合检索"留作后续优化项，
而不是在评测还没稳的时候把融合逻辑搬进服务端。
**面试被问到就照实说，并说明下一步：把 RRF 下推到 Milvus 可以减少一次往返，但要先证明两端结果一致。**

## 五、运维与踩坑

### Q8：删除数据会立刻释放空间吗？

**不会。** Milvus 的删除是**软删（标记删除）**，数据占用的空间要等
**compaction（合并段）** 才真正回收。所以：
- `delete` 后 `row_count` 可能不变（统计口径）；
- 大量删除后要触发 compaction 才能看到磁盘下降；
- **删除后立即用同样的向量检索，可能仍召回已删数据**（取决于一致性级别与 compaction 状态）。

**追问：这对我们意味着什么？**
我们的同步策略是全量 rebuild（drop collection），所以不受软删影响——
**drop 是彻底删除，不依赖 compaction**。选它正是为了避开这条坑。

### Q9：扩容与选主？

Coordinator 与 Proxy **无状态**，直接加副本即可；
query node / data node / index node **有状态**，扩容后需要**数据再均衡**（rebalance）。
选主靠 **etcd**。Coordinator 挂了会有短暂不可用，但因为元数据在 etcd，重启后能恢复。

## 六、选型对比（必考）

| 方案 | 类型 | 优势 | 劣势 | 何时用 |
|---|---|---|---|---|
| **Milvus** | 专用向量库 | 功能最全（多索引/多向量/混合检索）、可水平扩展、生态成熟 | 组件多（etcd/MinIO/MQ），运维成本高 | 大规模、生产级、要集群 |
| **FAISS** | 库（非服务） | 极轻、无服务、算法最全、单机性能强 | 无持久化、无并发服务、无过滤/多租户 | 离线实验、嵌入式、召回基线 |
| **pgvector** | PG 插件 | 与业务库同事务、SQL 生态、运维零新增 | 索引类型少、超大规模性能一般 | 已有 PG、向量规模中等 |
| **Qdrant** | 专用向量库 | Rust 实现、单二进制、过滤能力强 | 生态比 Milvus 小 | 中小规模、想少运维 |
| **Elasticsearch** | 搜索引擎 | 全文检索成熟、混合检索方便 | 向量检索性能与召回不如专用库 | 已有 ES、文本为主 |

**我们项目的实际（这条最有说服力）**：
我们**实现了两种后端**——内存（精确暴力）与 Milvus（HNSW），
**由同一个入口构造**（`build_index(milvus=...)`），所以"换后端前后指标是否一致"
是一个**可以验证的问题**，而不是一句声称。
而"内存后端"存在的意义是**离线可复现**：克隆即可跑，不需任何服务。

## 七、我们项目的真实数字（被追问时直接报）

| 项 | 值 |
|---|---|
| 部署 | milvus-standalone **v2.5.14**（+ etcd v3.5.18 + MinIO） |
| 索引 / 度量 | **HNSW（M=16, efConstruction=200）/ COSINE**，查询 `ef = max(64, top_k×4)` |
| 向量器 | BAAI/bge-small-zh-v1.5，**dim=512** |
| 集合命名 | `scout_<sha256(语料指纹 + 向量器身份)[:16]>` |
| 实测规模 | 8 篇 → **156** 个向量；**40 篇 → 988** 个向量 |
| **top-10 重合度** | **100%（8/8 查询，两档规模都是）** —— HNSW 的 ANN 召回在实测规模下无损失 |
| 建索引耗时 | 156 向量：内存 5.98s / Milvus 10.15s；988 向量：内存 37.96s / Milvus 45.04s |
| 检索延迟（156 向量） | 内存 **p50 15.7ms** ｜ Milvus **p50 9.3ms**（首次 104.5ms 为连接预热） |
| 检索延迟（988 向量） | 内存 **p50 92.1ms** ｜ Milvus **p50 21.5ms**（**约 4.3×**） |

### 三个能体现深度的追问应答

**追问 1：为什么 Milvus 比内存还快？**
> "因为我们的内存实现是**纯 Python 逐条算余弦**，它存在的目的是当**召回基线**
> （精确、可复现），不是做性能优化。瓶颈在解释器开销，不在算法。
> Milvus 是 C++ 的 HNSW 索引——**这个对比恰好说明：内存版是正确性基准，不是性能基准。**
> 如果要真比性能，应该把内存版换成 numpy 批量矩阵乘。"

**追问 2：重合度 100% 是不是在吹？**
> "不，是**规模太小**。156 个向量上 HNSW 几乎等价于暴力检索，召回必然 100%。
> **这个指标的真正价值要在规模上去测**——所以我下一步是把它跑到万级以上再看召回损失。
> 小规模上报 100% 是有意义的，但意义是'参数没配错'，不是'我们的 ANN 很好'。"

**追问 3：为什么不直接用 Milvus 的混合检索省一次往返？**
> "可以，但**优先级排在后面**。原因是评测可复现性：BM25+RRF 在本地算，
> 离线与在线走的是**同一份融合代码**；下推到服务端就出现两份实现，
> 而'两份实现是否等价'本身需要额外验证。在评测还没完全稳的时候，
> 我选择先保住'两条路径一致'这个性质。"

## 八、一张图记住要点

```
写入：Proxy → WAL(MQ) → data node → 对象存储(sealed segment) → index node 建索引
                                      ↑
                        不 flush 就在 growing segment，搜不到

查询：Proxy → query node（持有 segment）→ 按 metric 检索 → 聚合返回
              ↑ 索引选型决定召回/延迟；ef 是唯一运行时可调的旋钮

依赖：etcd（元数据+选主）｜MinIO（向量+日志）｜MQ（WAL）
删除：软删 → 需 compaction 才回收空间（我们用 drop 重建绕开）
```
