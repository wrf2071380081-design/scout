# scout 答辩稿

> 这份文档是**你自己用的面试资料**。每个设计点都按同一个结构写：
> **原理 → 为什么这么做（取舍）→ 别人大概率没想到的点 → 可能的追问和答法**。
>
> 面试里真正的区分度不在"我做过"，而在"我知道**为什么**这么做、
> 以及**在什么情况下会不适用**"。下面所有内容都围绕这两件事展开。

---

## 0. 一分钟电梯陈述

「scout 是一个长文档 Agentic RAG 框架。我不把它做成"又一个能问答的 RAG"，
而是把它定位成一个**能自证、能自愈、能自学的 Agent**：

- **能自证**：每个结论必须能追溯到检索到的证据 span，证据不足就明确拒答，而不是硬答
- **能自愈**：失败被归一成稳定的错误码，每类失败有恢复动作和预算上限，不会死循环
- **能自学（设计方向）**：完整轨迹被结构化记录，未来可以拿去教模型下次做得更好

技术上值得说的三件事：

1. **我拿到了真实的消融数据**——发现混合检索是第一杠杆（去掉它 MRR 掉 41.9pp），
   而主流说的「Auto-merge 会破坏排序」在我的语料上不成立。**它的效果是语料相关的，
   不能靠直觉决定，所以要靠消融实验。**
2. **我把"拒答"做成了可以统计的决策**——大多数系统的拒答率是 0，
   不是从不需要拒答，而是从来不拒答。这是有问题的安全信号。
3. **我给工具加了"人审"能力**——审批可以改参数，恢复时不重复副作用，
   还能从历史检查点时间旅行、且分叉不会重复副作用。」

## 1. 架构一图流（能复述就不慌）

```
用户问题
└─ ReAct 循环（模型每步自己决定调用什么、信息够不够、什么时候停）
   ├─ 知识检索..三级父子分块 → 混合检索（稠密 + BM25 + 加权 RRF）
   │             → Auto-merge（EXPAND/REPLACE 可切换）→ 词法重排
   │             → 双维充分性判定 → 归因门控
   ├─ 内置工具..计算器 / 日期（把模型的确定性缺陷挡在系统外）
   ├─ 动作工具..发邮件 / 建工单 / 删文件
   │             └─ 风险分级 → HITL 审批（可改参数）
   │                 → 副作用账本（血缘槽位幂等）→ 时间旅行分叉
   └─ 自愈编排..typed 失败 → 恢复动作表 → 预算 + 指纹抑制
```

一句话概括：**Agent 负责决定"做什么"，系统负责决定"什么时候停下来"、"要不要问人"、"出错了怎么办"。**

## 2. 核心设计点

### 2.1 ReAct 循环 + 四重预算

**原理。** ReAct 让模型每步自己决定：调用什么工具、信息够不够、什么时候停。
但"让模型自己决定"和"系统可控"是一对矛盾。所以我给循环上了四道硬约束：
**步数上限、工具调用总数上限、同参数重复调用上限、墙钟截止**。任何一道撞线，状态落盘并返回。

**为什么这么做。** 没有预算约束的 Agent 死循环很常见：同一个工具、同一组参数被反复调用，
一次请求被放大成几十次外部调用，而且失败时没有"系统该停下来"这个状态，只能烧 token 烧到超时。

**别人没想到的点。** 预算耗尽不能"就报错"。死循环里的系统不能停在"挂了"，
要能停在**"我为什么停下来"**——有明确的 stop_reason、有落盘检查点、有可审计的轨迹。

**追问与答法。**
- *「预算怎么定？」* → 不是直觉定"8 步 12 次"。这是语料和系统能力的标定问题，
  **要看轨迹实验**——观察每条轨迹实际走了多少步、碰到超限的比例，再定。
- *「重复调用怎么处理？」* → 同参数调用超过阈值就不再执行，而是把"换参数/换工具/直接作答"
  用纠偏提示回灌给模型，让它自己修正，而不是硬拦。

---

### 2.2 自愈编排（失败分类 → 恢复动作表 → 指纹抑制）

**原理。** Agent 的失败很少是"模型不会"，大多是**运行时状态问题**：provider 超时、
工具参数写错、上下文过期、证据互相冲突、重试死循环。这些事的共同点是——
**它们可以被识别，也可以被对策**，但需要一层专门负责这件事。

**为什么这么做。** 把失败都塞给模型，最后只有"答得不对"和"挂了"两种状态，
监控上看不到任何一种。所以我把失败归一成 typed 错误（稳定错误码 + 阶段 + 是否可重试），
然后是一张**显式的恢复动作表**——每类失败对应一个恢复动作，不是散落的 if。

**别人没想到的点。** **同一个失败指纹，在预算内只允许恢复有限次。** 没有它，
"重试一次"会在嵌套调用里被放大成十几次外部请求。这是防死循环的核心。

**追问与答法。**
- *「恢复动作表怎么来的？」* → 从错题集反推——哪些失败类型最常见，每类该配什么动作。
  我先定失败分类，再定每类的恢复动作，是按证据来定的，不是拍脑袋列的。
- *「什么叫 fail-closed？」* → 未登记的工具**默认按"有副作用"处理**，而不是默认放行。
  安全侧的错误，不应该由系统替用户做。

---

### 2.3 三层记忆 + bi-temporal 有效期

**原理。** 把历史对话塞进向量库按相似度召回，是最容易做的版本，也是最容易出问题的版本——
它分不出**"现在为真"和"曾经为真"**。用户上个月说"我在做 Java"，这个月改口说"转 Go"，
两条记忆的向量同样接近，召回谁几乎随机。系统会自信地重复一个早已过期的事实。

**为什么这么做。** 给每条记忆加 `valid_from` / `valid_until` 双时间戳；
写入冲突的新值时，旧值**不是删除，而是被标记失效并指向继任者**。
召回默认只认"现在有效"的；"什么时候变的、变成了什么"本身作为事件保留，可追溯。

**别人没想到的点。** 失效不是销毁，而是**可见的生命周期**。审计或排查问题时，
"这条事实什么时候被谁覆盖"能直接查出来——很多系统删了就再也追不回了。

**追问与答法。**
- *「为什么不直接用 Mem0 / Zep？」* → 不是重来，是保留选择权。当前实现只要把"失效可见"
  做强，替换成已有的框架只要落一处；而且如果你后续要接 LongMemEval 这类评测，
  边界越清晰越好换。
- *「会召回过期事实吗？」* → 召回默认 `include_expired=False`。
  **`include_expired` 只有在你显式查询历史时才允许**，比如"我上次改的是什么"。

### 2.4 双维充分性判定 + 拒答校准

**原理。** RAG 整体提升了下游能力，却**降低了模型适时说"不知道"的能力**——
给它一段"看起来相关"的材料，它更倾向于拼一个答案，而不是承认材料不够。

**为什么这么做。** 主流只有一个判定：加权覆盖率。
但政策类语料里"建设""标准"几乎每篇都出现，一个完全没办法回答的问题
（"火星殖民基地的建设标准是什么"）也能被撑到过半覆盖率，绕过门控。
所以我加第二维：**`focus_coverage`——多字词/拉丁词这些具体概念词的未加权覆盖**。
它回答的问题是"问题真正在问的东西找到了没有"，而不是"材料整体对不对题"。

**别人没想到的点。** 聚焦词**刻意不加权**——加权会被跨词边界的伪双字组主导
（"建**设标**准"切出的 `设标`，df=1 因而 IDF 极高），把噪声放大。
这个细节只有真正撤过分词器的人才会想到。

**追问与答法。**
- *「纯词法为什么不够？」* → 它有天花板，因为"词汇重叠"不等于"真的能回答"。
  这个方法论的诚实之处就在于我能说清它**什么时候会错**；生产环境要换成模型侧判断。
- *「阈值怎么定？」* → 在语料上先跑探索，再挑一个"误拒率可接受"的点。
  换权重函数必须重标阈值——**同一个 0.5，在未加权与 IDF 加权两种尺度下意义完全不同**。

### 2.5 注入防护（检索侧三层）

**原理。** 检索到的文档是**不可信输入**。攻击者不用攻破你的系统，
只要让一段恶意文本进入语料并排进 Top-K，就可以了（间接提示注入）。
主流做法是"加过滤规则"，但载体很多——隐藏的 HTML、`display:none`、
Unicode 零宽字符、ARIA 标签、图片替代文本——单点拦截挡不住所有载体。

**为什么这么做。** 按三层叠加：
**结构消毒 + Unicode 归一化 + 归因门控**（生成端只允许输出能被证据 span 支撑的内容）。
OpenRAG-Soc 这个 benchmark 已经验证了——单独一层挡不住，三者叠加才能把攻击成功率
压到个位数，而且延迟和效用损失极小。

**别人没想到的点。** **归因门控不是锦上添花，是防线的一半。**
就算注入成功混进上下文，归因门控也会把没证据支撑的部分删掉。

**追问与答法。**
- *「三层关系为什么要成立？」* → 结构消毒挡隐藏载体，Unicode 归一化挡零宽/仿形载体，
  归因门控挡"就算进来了也不让出来"。三者覆盖不同的攻击面。
- *「为什么不直接拒答注入的文档？」* → 那不是防线的意义。
  这是**兜底**——保护更多是防意外，不是给用户挑哪份文档的权利。

---

### 2.6 Auto-merge 双模式 + 语料相关性

**原理。** 经典 Auto-merging 把命中叶子块替换成父块，主流说它会破坏排序。
我把它拆成双模式：**EXPAND**（合并上下文，检索身份仍是叶子块）与**REPLACE**（替换身份为父块），
并用同一配置做了消融，结果反直觉：**REPLACE 反而比 EXPAND 高 +6.8pp MRR**。

**为什么这么做。** 「REPLACE 更好」是**另一个项目**上得到的结论；
而这份语料上**REPLACE 反而更好**。两条数据拼到一起才看清真相——
**Auto-merge 的行为是语料依赖的**，不是全局最优或全局最劣。
这正是每个模块都做成可开关的原因：**靠消融数据来决定，不靠主流说法。**

**别人没想到的点。** 能大面积影响一段实现长期调优的一个约束：**「检索单元与展示单元必须解开」**。
重排器时必须拿"检索身份"（叶子块原文）去排序，而不是拿"给你看的上下文"——
否则 EXPAND 会被自己稀释，这也是消融里真实暴露过的实现 bug。

**追问与答法。**
- *「你的结论跟主流不一致，为什么？」* → 因为主流结论是"特定语料、特定重排器"。
  我的消融直接把"你的语料 + 你的重排器"换成了这个具体场景，所以结果不同。这件事本身就说明：
  **该问的不是"哪个更好"，而是"在你的条件下哪个更好"。**
- *「这是怎么修的？」* → 重排只认叶子块原文。改完之后
  EXPAND 不再自我稀释，它的负贡献就消失了。

### 2.7 四层评测

**原理。** 大多数 RAG 项目只在看"答案对不对"，所以永远不知道坏在哪层。
我把评测拆成四层：**检索 / 生成 / 安全 / 轨迹**，共 23 项指标，
其中**轨迹层**（平均步数、工具调用数、工具失败率、重复调用率、预算终止率）
和**拒答校准**是大多数项目缺失的。

**为什么这么做。** 因为大多数系统的失败分布在四层里有一项是零，
不是能力问题，是**根本没人去看**。
把它拆成四层、再按 14 类标签切片，你才能回答"坏在哪一类"。

**别人没想到的点。** **拒答率恒为 0 不是"系统从不需要拒答"，而是"系统从来不拒答"。**
拒答率只有在是一个实际会被触发的指标时才说明它存在过。
把这个指标照出来，是这套评测的价值。

**追问与答法。**
- *「gold 为什么用文本片段而不是 chunk_id？」* → chunk_id 依赖分块参数，
  改参数就全废。"这段文字应当被检索到"与分块策略解耦，
  这样做了分块消融之后废旧集还能用。
- *「如何评测终于有意义？」* → 把整体分数切片到具体标签：
  表格类坏 → 分块问题；错别字类坏 → 改写问题；无知识类坏 → 拒答问题。

### 2.8 HITL（人工介入）★ 本项目的深度项

**原理。** "给 Agent 个人工确认"听起来很简单——在工具调用前弹个框问一下就是了。
但一旦要求**中断能跨进程、跨小时、跨重启存活**，问题立刻变形。
我做了四件事：

1. **中断点是声明式策略，不是散落代码。** 按风险分级（SAFE / CONFIRM / REQUIRED），
   不是一刀切——查知识库也要审批的 Agent 没人会用。
2. **审批结果能携带参数修改。**「批准，但把金额从 100 万改成 10 万」
   是审批的真实形态，不是二元开关。
3. **恢复时不重复执行副作用。**
4. **没人审批时要有兜底**，默认 fail-closed。

**为什么这么取舍（重点）。**

**第一，状态用纯数据表示，不 pickle 对象图。** 这是整个工程质量的分水岭。
改了代码、改了类位置，pickle 的历史快照全废；
而且它会把 LLM 客户端、连接池、闭包一起序列化，把内部写进磁盘。
所以状态只能是数据——这个"不方便"是刻意的，是可恢复性的前提。

**第二，副作用幂等键建在"血缘"上，不是当前 run_id。** 时间旅行分叉换了一个 run_id，
但血缘没变——所以"从过去分叉出一个新 run"不会把已发出的副作用再发一次。
`fork` 继承**最新的副作用账本**（副作用是世界的客观事实，与历史状态回退无关），
所以就算你把"发邮件之前"的状态捞出来重跑，也不会再发一次邮件。

**第三，补偿事务是显式声明的。** 工具声明 `side_effects` 与 `compensator`（如 send_email → recall_email）。
这样"新增一个工具要不要审批"跟着工具定义走，不用去改策略代码；
而**不可补偿的工具一律走 REQUIRED 级审批，且不提供免审开关**。

**别人没想到的点。**
- *审批不能对所有副作用都弹*——查知识库也要审批的 Agent 没人会用，所以要有风险分级。
- *审计必须能区分"真人决定"与"超时策略的自动决定"*——`HumanDecision.source` 分 human/timeout_policy，
  不然就是给审计埋雷。
- **中断时是 suspend，不是 block**——挂起后进程可以退，审批可以来自几个小时后、另一台机器。
  它把"人的响应时间"与"进程生命周期"解耦了。用 `input()` 阻塞式确认是设计阶段的错误。

**追问与答法。**
- *「恢复时怎么不错？」* → 从断点继续，不是从头重跑。
  幂等键建在**调用槽位**（第几步第几次调用）而不是参数上，
  所以就算参数被审批人改过，也能稳定识别"这是同一次调用"。
- *「审批超时怎么办？」* → 默认 reject（fail-closed）。
  没有人做决定时，系统不应该替人做那个更危险的默认选择。
- *「fork 为什么不能 rollback？」* → 已发生的事改不回去（邮件已发出）。
  正确的操作是**新建一条时间线**，而不是伪装历史不存在；
  要撤销才算补偿事务（`rollback_plan`）。

## 3. 我可以讲出的"别人大概率没做"的几个点

- **Auto-merge 的效果是语料依赖的**，不是常识——他们没在同一实现上把 REPLACE 和 EXPAND 各跑一遍消融。
- **拒答恒为 0 从不关闭这个问题的系统**——他们只报了"准确率"。
- **注入防护是三层叠加**（结构消毒 + Unicode 归一化 + 归因门控），不是单层过滤。
- **记忆的失效与版本是可追溯的**——他们删旧的不记历史。
- **HITL 的副作用幂等 + 血缘分叉**——大多数演示里没时间讲这么深。

## 4. 我会主动说的局限（主动说，比被问出来好）

这是面试里最该主动说的一类，不要等被问出来：

1. **评测样本量只有 19 条手选 + 200 条自动生成**——数字只具方向性，不构成统计结论。
2. **离线实现的答案质量有限**——`HeuristicLLM` 是词法抽取，它的作用是让流程**可复现**，不是"能打"。
   配置真实模型后指标需要重新测量。
3. **哈希向量器不是语义向量器**——它是为了保证"克隆即可跑"，位置很合适，
   不能替代 BGE 或任何模型级的检索质量。
4. **大多数"出了什么问题"的诊断结果**，最终都要在更大的评测集上重跑一遍验证。
5. **长期记忆还没有**——三层记忆的`语义记忆`目前是显式可替换的设计，没有精细的固化与来源推断。

补一句可以很自然地说出来的收尾：

> **这个项目的价值不在 69.5% 还是 94.7% 的 Recall@5，
> 而在为了测出这两个数字，那些每一个模块的确切意义必须被定位清楚。**
> 消融能让"我上了 Auto-merge"变成一句有代价的话，而不是一句无代价的简历话术。

## 5. 应对一击必杀的追问（保持自己的降低中加答案）

**「Auto-merge 的消融为什么跟主流说法不一致？」**
主流结论是"REPLACE 会稀释排序"的长文档语料。
我的消融用的是**同一份编排、同一个检索器、不同的语料**，
所以结论不同。这不是"主流错了"，而是**"主流说法随语料条件成立"**。
换到自己的场景就该先跑消融再下结论——这正是每个模块要做成可开关的原因。

**「为什么每个模块都可开关？」**
因为消融的前提是——只有当**每个模块能单独打开和关闭**，
才能把"它到底有没有用"编上名字。不是代码洁癖，是实验需要。

**「为什么说 Auto-merge 是"你的语料与你重排器"的实验问题？」**
因为它的行为会被"上下文如何被评价"左右：
词法重排器会偏好叶子块的紧凑文本，从而给 EXPAND 一个负向差；
REPLACE 如果捡出了更battle 的父块，就反而正向。
同一段实现，你换一个重排器结果就变了。所以这是**从你的条件出发**的问题。

**「为什么这么强调身份可追溯（chunk_id / 内容 hash / document_version）？」**
因为 trace 只能存身份、不能存正文——不然 trace 会撑爆，还会把敏感内容写进日志。
而一旦出错，没有身份可追溯就比没有答案更可怕。

**「为什么手写 LLM 抽象层而不是直接用现有 SDK？」**
因为只有抽象层能让你把**可控的离线确定性实现**和**真实的在线模型**无缝切换。
评测需要可复现，现有 SDK 都绑网络；没有这层，评测不可能离线跑。
这也是对成本负责——不用为了跑 demo 就去申请 API key。

**「你已经有了失败分类，为什么不给模型分层策略，比如强模型做实作、弱模型做监控？」**
因为模型分层本身也是个"实验问题"。它讲的是成本与品质的取舍，
但它也不是普适的答案——强模型做哪一步、弱模型做哪一步，取决于每个动作的出错成本。
对一份独立、人人可复现的项目来说，宁肯把每个动作先可靠做出来，
而不是把"模型怎么选"这种面向生产的取舍提前固化。
这个选择跟"是否需要 200 条标注才谈效果"是同一件事：先让系统每个动作的边界成立，
再说该用强模型还是弱模型，而不是反过来。

## 6. 面试胜率最高的三个准备习惯

1. **第一段电梯陈述能讲出一分钟**——用"一件事"和"一个真实数字"开头。
2. **每个设计点都能讲出"为什么"**——不是"我做了什么"而是"我知道为什么这样"。
3. **主动说五个局限**——而不是等被问出来。

---

> **面试里真正的杀伤力，不是"我做过多少件事"？而是"我做了一件能被追究到底的事"。**
