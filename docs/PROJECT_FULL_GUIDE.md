# 第 0 层：RAG 是什么，Agentic RAG 又是什么

## 0.1 大模型有两个天生的硬伤

**硬伤一：它不知道你的资料。**

大模型是在公开互联网上训练的。你公司的内部制度、你手上的那份年报、
昨天刚发的政策文件——**它没见过**。你问它，它要么说不知道，要么（更糟）编一个。

**硬伤二：它不知道自己不知道。**

这是更麻烦的那个。当你把一段不相关的资料塞给它，问"根据这段资料回答 XX"，
它**不会说"这段资料答不了这个问题"**。它会用这段资料，编一个读起来很顺的答案。

为什么？因为它被训练成"要给出有用的回答"。在它眼里，"我不知道"是个失败的答案。

> 打个比方：就像一个特别想帮你、但**又特别爱面子**的实习生。
> 你问他一个他不知道的事，他不会说"我不知道"，他会顺着你给的材料，
> 编一个听起来很合理的故事。

## 0.2 RAG 的办法：把"闭卷考试"改成"开卷考试"

**RAG** = Retrieval-Augmented Generation（检索增强生成）。

思路很朴素：既然模型不知道你的资料，那就在它回答之前，**先把相关资料找出来塞给它**。
就像考试从闭卷改成开卷——不要求你背下来，但要求你会查。

流程就三步：

```
问题 → 检索（找出相关资料）→ 生成（让模型看着资料回答）
```

## 0.3 但基础 RAG 有个致命缺陷

**它只检索一次。**

如果第一次没找对，它就拿着错的东西硬答——**而且它不会告诉你它答错了。**

三个典型的翻车现场：

| 场景 | 会发生什么 |
|---|---|
| 库里根本没有答案 | 它拿不相关的段落编一个 |
| 问题需要跨两份文件 | 只找到一份，另一份也"顺手"编出来 |
| 问得很模糊（"这个标准怎么规定的"——哪个标准？） | 它随便挑一个理解就答了 |

## 0.4 Agentic RAG：从"一条直线"变成"会做决定的流程"

**Agentic** 的意思是"有主体性的、会自主决策的"。

区别在于：基础 RAG 是一条**直线**（检索→生成，结束）。
Agentic RAG 是一条**有岔路口的流程**——它在每个岔路口做判断，然后决定下一步去哪：

```
问题 → ① 这问题简单还是复杂？复杂的拆成几个小问题
     → ② 检索
     → ③ 这些资料够不够回答？
           够    → 答题
           不够  → 换个说法再检索一次
           太模糊 → 反过来问用户"你是指哪个？"
           真没有 → 老实说"我没有这方面的资料"
     → ④ 答完之后再检查一遍：哪句话没有依据？有就重写
```

**这就是我们这个系统的核心。** 后面所有的设计，都是为了把这几个岔路口做对。

# 第 1 层：一次问答到底走了哪些步

先看全景。用户问一句话，系统内部实际跑过的步骤（这些步骤在系统里都有记录，
可以逐条查）：

```
用户问题
   │
   ├─ 1. 复杂度判定      ← 简单问题直接检索；复杂问题先拆子问题
   │
   ├─ 2. 检索（两路并行）
   │      ├─ 向量检索（按意思像不像）
   │      └─ 关键词检索（按字面匹不匹配）
   │      └─ 两路结果融合
   │
   ├─ 3. 父块合并        ← 命中的小片段，把它的上下文补回来
   │
   ├─ 4. 重排            ← 用专门的模型把这批候选重新排一次序
   │
   ├─ 5. 证据评估  ★     ← 关键岔路口：这批资料够不够回答？
   │       ├─ 够 → 继续
   │       ├─ 不够 → 改写查询，回到第 2 步（有次数上限）
   │       ├─ 模糊 → 问用户澄清
   │       └─ 没有 → 拒答
   │
   ├─ 6. 安全消毒        ← 防止资料里藏了"忽略以上指令"这种注入
   │
   ├─ 7. 生成回答        ← 强制标注来源编号，禁止推测
   │
   └─ 8. 归因校验  ★     ← 逐句检查：这句话能在资料里找到依据吗？
            ├─ 都在 → 输出
            └─ 有编的 → 带着"你上次编了这些"重写一遍；还不行就拒答
```

**带 ★ 的两步是这个系统的灵魂**——第 5 步决定"要不要答"，第 8 步决定"答得靠不靠谱"。

# 第 2 层：Agentic 到底体现在哪（五个决策点）

"Agentic"这个词现在被用得很泛。具体到我们这个系统，它是**五个真实的决策点**：

## 决策点 1：这问题要不要拆？

系统先问自己一句："这问题简单还是复杂？"

- **简单**：答案集中在一份文档的一小段里（"到 2027 年要制定多少项标准？"）
- **复杂**：需要跨文档、多跳推理、对比多个对象（"对比 A 和 B 各自的 2027 目标"）

判断为复杂，就**拆成 2~4 个能独立检索的小问题**，分别去检索。
因为一个查询很难同时把两份文档的相关内容都捞回来。

> 这在系统里叫 `complexity` 和 `subquestions` 两个阶段，都能在记录里看到。

## 决策点 2：资料够不够？（这是最关键的）

系统让模型评估四项：相关性、覆盖度、能不能答、问题本身有没有歧义。
然后从四条路里选一条：

| 走到哪条路 | 什么情况 |
|---|---|
| **直接作答** | 资料齐全，可以答 |
| **改写再检索** | 可能是我第一次问的姿势不对，换个说法重试 |
| **问用户澄清** | 问题本身缺条件（"这个标准"——哪个标准？） |
| **拒答** | 库里确实没有 |

**关键设计：这一判断由独立的评估步骤做，不是让答题的模型自己看着办。**
因为答题的模型太想答题了——它永远觉得"差不多可以答"。

## 决策点 3：答完之后，有没有编？

即使资料够，模型也可能在生成时"顺手"加点资料里没有的东西。

所以生成之后还有一道**归因校验**：把答案拆成句子，逐句检查——
**这句话能在给出的资料里找到依据吗？**

- 都有 → 输出
- 有编的 → **带着具体的失败原因**（"你上一版有 3 处没有依据"）重新生成一次
- 还有 → 拒答

> 这就像交卷前自己先对一遍答案出处。

## 决策点 4：出错了怎么办？

系统把错误分成类型，每类对应一套**恢复动作序列**：

| 错误类型 | 恢复动作 |
|---|---|
| 供应商超时/连不上/限流 | 重试 → 降级到备用通道 → 停止 |
| 模型返回的格式不对 | **重新提示它**（告诉它哪里错了）→ 重试 → 停止 |
| 工具参数不合法 | 把校验错误回灌给模型让它自己修 → 停止 |
| 同一工具被反复调用 | 抑制（防止死循环烧钱） |

**"重新提示"和"重试"是两件不同的事**：前者是把错误原因告诉模型让它改，
后者是原样再发一次。混为一谈会浪费大量调用。

## 决策点 5：要动外部世界时，先停下等人

如果 Agent 决定调"发邮件"这类**有副作用**的工具，它会停下来等人审批。
审批通过才执行。

更难的部分在恢复：审批通过、从断点继续跑的时候，**那封邮件不能重发**。
这件事靠"副作用按调用位置记账 + 幂等"解决。

# 第 3 层：每一层具体怎么做（到参数）

## 3.1 数据层：把"能读"变成"能用"

**要解决的问题**：真实长文档转成文本之后是脏的。双栏排版被读成一栏（左右两栏文字交错，
句子读不通）、跨页表格缺表头、同一份文件导入多次。

**为什么严重**：这类问题**不报错**。它只会让"召回率下降、回答质量下降、拒答率上升"
一起出现，你去查检索代码——代码没错；换模型——换了也没用。
**因为雷埋在几天前的一次文档导入里，而且它一声不吭。**

**做了什么，效果多少**（在一份 40 篇真实语料上实测）：

| 处理 | 效果 |
|---|---|
| 双栏检测 + 阅读顺序重排 | 2 篇双栏文档**重排 660 行** |
| 跨页表格补写表头 | 合成样本上验证通过 |
| 精确去重（内容哈希，完全一样才删） | 丢掉 86 段 |
| 近似去重（SimHash，差几个字也算重复） | 丢掉 29 段 |
| **合计** | **挡下 115 段，占 886 段的 13%** |

**那 13% 为什么重要？** 它们会占满检索结果的 Top-K。
用户看到"三条一样的结果"，而真正需要的那条**根本没进榜**。

### 分块：为什么要切成三级

文档太长，整篇塞给模型不现实（贵、而且重点被稀释）。所以要切。
但**切小了丢上下文，切大了不准**。做法是切三层：

| 层级 | 大小 | 重叠 | 作用 |
|---|---|---|---|
| L1（父块） | 2400 字 | 400 | 提供完整上下文 |
| L2（中块） | 1600 字 | 200 | 折中 |
| L3（叶块，实际用于检索） | 800 字 | 100 | 检索精确 |

**检索时用最小的 L3**（精确），**命中后把它的父块补回来**（有上下文）。
这就是"检索准 + 上下文全"两件事的折中。

> 重叠（overlap）是为了防止"关键句正好被切在分界线上"——所以相邻块共享一部分内容。

## 3.2 检索层：为什么要两路检索

**两路各自的盲区：**

- **向量检索**（稠密）：把问题变成一串数字，找"意思像"的。
  你问"怎么退钱"，它能找到写着"退款流程"的段落——**强在同义改写**。
  但**对精确词不敏感**：你问标准号"GB/T 12345"，它可能给你一堆泛泛的"标准"内容。
- **关键词检索**（稀疏，BM25）：**强在精确匹配**，弱在同义。
  你问"怎么退钱"，它找不到"退款"。

**所以两个都跑，然后把结果融合。** 融合规则叫 RRF：
"在两个榜单里都排前面的，更可能是真正相关的"。

### 然后加一层重排（rerank）

两路融合后有一批候选（16~32 条），但**排序还不够准**。

重排用的是 **cross-encoder**——它把"问题和每条候选**一起**"送进模型打分，
比"各自变成向量再比"准得多。缺点是慢，所以只对候选池做（不能对全库做）。

**实测这层重排值多少**（300 条配对比较）：

| 重排器 | Recall@5 | 说明 |
|---|---|---|
| 词法重排（基线） | 26.8% | 便宜的替代方案 |
| cross-encoder | 38.5% | 真实的那个 |
| **差量** | **+11.67 个百分点**，置信区间 [8.83, 14.67] | 区间不跨零 → 是真效果 |

### 向量存在哪：Milvus

候选池和向量库是两件事：
- **向量库（Milvus）**负责"从几十万段里快速找出最像的 16 条"
- **重排**负责"把这 16 条排出正确顺序"

我们**两种后端都实现了**：内存（精确但有上限）和 Milvus（可扩展）。
两种由同一个入口构造，所以"换后端前后指标是否一致"是**可以验证的**，
而不是一句声称。

## 3.3 生成层：怎么让它不敢编

生成时的提示词里有几条硬约束：

1. **每个结论后面必须标注来源编号**（形如 `[1]`、`[2]`）
2. 证据不足以支撑某个结论时，**明确说"现有资料未涵盖"，不要推测**
3. 如果全部证据都答不了，**直接回答"无法回答"，不要编造**
4. 不要引用编号之外的内容

然后第 8 步的**归因校验**会真的去检查它有没有做到第 1 条。

## 3.4 运行层：钱、延迟、状态

这一层解决"调用怎么发生"：

- **语义缓存**：问过的问题不再花钱。但缓存要带**作用域**
  （任务 + 证据指纹 + 模型版本）——同一问题换知识库必须失效，
  否则会把**旧答案喂给新数据**。
- **模型路由**：低难度任务（分类、打分、改写）走快模型，重任务走旗舰模型。
- **预算**：调用前预扣、硬上限、用完结算——防止一个任务把账单烧穿。

**这三层的包装顺序不能乱**：

```
缓存（最外） → 预算（中间） → 路由（最内） → 真实模型
```

- 缓存在最外，因为**命中不花钱**。要是预算套在外面，
  一次"本来免费"的命中会先被预算拦下，用户看到"预算不足"——而这次根本不需要钱。
- 路由在最内，因为**预算需要先知道用哪个模型，才能算对价格**。

# 第 4 层：测试数据长什么样（公开的 + 自己的）

## 4.1 为什么要两套

只用自己造的数据，会有"自己给自己出题"的风险——**你可能无意中把题造得适合你的系统**。

所以额外跑一个**公开基准**：别人出的题、别人定的标准答案、我不可能作弊。
它的作用是**提供一个不受我控制的对照**。有意思的是，它暴露的问题最多。

## 4.2 公开的：MuSiQue-Ans

**是什么**：一个多跳问答数据集。"多跳"的意思是——**答一个问题要串联好几段信息**，
不能在一段里直接找到答案。

举例（示意）：

> 问：**那位设计了 XX 桥的工程师，他的母校现在有多少学生？**
> 要答这个，得先找到"XX 桥是谁设计的"（第 1 跳），
> 再找到"这个人的母校是哪所"（第 2 跳），
> 再找到"这所学校现在的学生数"（第 3 跳）。

**为什么用它**：它专门考"能不能把散落多处的证据串起来"。
而我们的系统正好在解决"证据不够就拒答"——**多跳题是最好的试金石**，
因为它天然容易证据不全。

**怎么用**（重要，这决定了数字可比性）：

- 文件里有 2417 条，我们**取前 N 条作为冻结样本**
- **关键设置：每道题的检索范围不是它自己那几段，而是把一批题的段落合在一起**
  （我们跑 300 条时，检索池是 **5650 段**）。
  这样检索才真的是"大海捞针"，而不是"在 20 段里挑"。

## 4.3 自己的：longdoc-gold

**语料**：**40 篇真实中文长文档**，两类——
- 政策与标准（云计算标准体系、低空经济、电力市场规则、氢能试点……）
- 上市公司年报摘要

**标注**：**19 条人工标注的问题**，覆盖 **14 种查询类型**——
单一事实、参数阈值、定义解释、跨文档、多跳、对比、时间版本、表格、
歧义、近似实体、错别字、长问题、无知识（应拒答）、提示注入。

**为什么要 14 类**：因为不同类型的题**失败原因完全不同**。
参数题失败通常是"重排没把正确段落排上来"；
跨文档题失败通常是"根本没检索到第二份文档"。
如果你只有一个平均分，你看不出这些问题。

**这套数据的实测结果**：

| 指标 | 值 | 说明 |
|---|---|---|
| Recall@1 | 78.95% | 第一名就找对的比例 |
| Recall@5 | 89.47% | 前五名里找对的比例 |
| 目标来源命中率 | 100% | 至少找对了文档 |
| 拒答正确率 | 100% | 该拒的都拒了（**注意：分母只有 2 条**）|
| 误拒率 | 0% | 没有"本来能答却拒了" |
| 作答率 | 68.42% | |

## 4.4 两套数据各自暴露了什么

| 数据集 | 暴露的问题 |
|---|---|
| MuSiQue（英文） | 作答率只有 24% —— 因为语料是英文、向量模型是中文专用的，**语言错配** |
| longdoc（中文） | 同一套门控，作答率 68.4%、误拒率 0% —— 说明**门控本身是校准过的** |

**两套放一起看，才把"24% 是不是太保守"这个问题回答清楚。**
单看一个数字，你只会觉得系统很笨。

# 第 5 层：指标词典（外行版）

## 5.1 检索层指标

### Recall@K（召回率@K）

**问题**：正确答案在不在前 K 名里？

**类比**：你让助手去书架上找 3 本相关的书。
Recall@5 = "我让他拿回 5 本，该找的那几本在不在里头"。
**不关心顺序，只关心有没有。**

**我们的数字**：Recall@5 = 89.47%（长文档语料）

**为什么用 @5**：因为最终要送给模型的证据大概是 5 条左右，
排在第 8 名的正确内容，实际用不上。

### MRR（平均倒数排名）

**问题**：正确答案**排在第几名**？

**怎么算**：第一名得 1 分，第二名得 0.5 分，第三名得 0.33 分（取倒数），然后平均。

**类比**：还是找书。Recall 关心"有没有找到"，
MRR 关心"**第一本是不是就对了**"——找是找到了，但翻到第 5 本才发现，
体验完全不同。

**我们的数字**：MRR = 0.726。换个说法：**平均而言正确答案排在第 1.4 名左右**
（因为 1/1.4 ≈ 0.71）。

**为什么它重要**：因为模型只看到前几条证据。正确内容排第 5 还是排第 1，
直接影响它能不能答对。

### nDCG@10

**问题**：排序整体的质量怎么样？

**类比**：MRR 只看"第一个对的排第几"，nDCG 看**整个榜单的前 10 名排得好不好**。
如果相关的内容都挤在前面，分数高；零散分布，分数低。

**我们的数字**：nDCG@10 = 73.79%

## 5.2 "pp" 是什么意思（面试高频）

**pp = percentage point = 百分点。**

这是最容易搞混的地方：

| 说法 | 意思 |
|---|---|
| 从 68% 到 73%，涨了 **5pp** | **绝对差**：73 − 68 = 5 |
| 从 68% 到 73%，涨了 **7.4%** | **相对增幅**：(73−68)/68 = 7.4% |

**两者都合法，但必须说清是哪个。** 说"提升了 5%"很容易被理解成 5pp，
反过来也一样。所以业内惯例是：**用 pp 表示绝对差**。

**我们的例子**：关掉混合检索，MRR 从 68.6% 掉到 26.7%，
所以是"**−41.9pp**"（绝对掉了 41.9 个百分点），
而不是"下降了 41.9%"（那会算成下降 61%）。

## 5.3 置信区间与 bootstrap

**问题**：我测了 300 条，得到 38.5%。这个数字有多可信？

**类比**：你不可能问遍全国所有人"支持不支持"，所以你只问 1000 个人。
但换一批 1000 人，结果会不一样——**置信区间就是"这个波动范围能有多大"**。

**bootstrap 的做法**：从你已有的样本里"有放回地"反复重抽（比如抽 1000 次），
每次都算一遍指标，看这 1000 个结果的分布——取中间 95% 的范围作为置信区间。

**为什么它有用**：300 条时区间是 [35.0, 42.2]（±3.6pp），
50 条时是 [39.0, 57.0]（**±9pp**）。

**区间宽度本身就是"这个样本量能支撑多强的结论"的度量。**
拿一个 ±9pp 的数字宣布"我们提升了 5 个百分点"，是没有意义的——
因为那个提升完全可能是抽样波动。

## 5.4 生成与安全层指标

### 支撑率（support_rate）

**问题**：答案里的句子，有多少能在资料里找到依据？

**类比**：学生写论文，每句话后面都要有引用。
支撑率 = "有多少句话真的有出处"。

**我们的数字**：归因支撑率 100%（长文档语料）

### 覆盖度（coverage）

**问题**：资料对问题的各个要点覆盖了多少？

**类比**：题目问了三个方面，你找到的资料只提到两方面——覆盖度就是 2/3。

**为什么要它**：这是"够不够回答"这个判断的主要依据。
覆盖度太低就说明资料不全。

### 幻觉率（hallucination_rate）

**问题**：**该拒答的题，它却答了**（编了）多少？

**我们的数字**：0%（在两套语料上都是 0）

### 误拒率（false_refusal_rate）

**问题**：**本可以答的题，它却拒了**（怂了）多少？

**我们的数字**：中文长文档 0%；MuSiQue 上偏高

### 为什么这两个必须分开

如果只看一个"拒答率"，你分不清系统是**谨慎**还是**笨**：

- 拒答率 70%，可能是"它很有把握才答"（好）
- 拒答率 70%，也可能是"它什么都不会，全在推"（差）

**只看一个数字，这两种情况长得一模一样。**

分开之后你才能说："我现在幻觉率 0% 但误拒率 8%，说明门控太严了，可以松一点。"
而且这两个指标**天然互相拉扯**——松门槛，幻觉率升、误拒率降。

### 作答率（answered_rate）

**问题**：100 个问题里，它选择回答了多少个？

**注意**：这个数字**单独看没有意义**。24% 的作答率配 0% 幻觉率，
和在 0% 幻觉率下冲到 80% 作答率，是完全不同的两件事。
所以它必须和幻觉率一起看。

## 5.5 轨迹层指标（Agent 特有）

| 指标 | 问题 |
|---|---|
| 平均步数 | Agent 平均走了几步？（太少=没充分检索，太多=绕圈）|
| 工具失败率 | 工具调用失败的比例 |
| 重复调用率 | 同一个工具同样参数重复调了几次（死循环的征兆）|
| 预算终止率 | 有多少任务是因为预算耗尽而停的（太高说明预算太紧或任务太重）|

# 第 6 层：全部参数速查

## 6.1 模型与维度

| 用途 | 模型 | 维度 / 参数 |
|---|---|---|
| **向量化（embedding）** | `BAAI/bge-small-zh-v1.5` | **512 维** |
| **重排（rerank）** | `BAAI/bge-reranker-base` | cross-encoder |
| **生成/判断** | OpenAI 兼容网关（测试期用 `kimi-k3`）| — |
| **图片 OCR（可选）** | 本地 `glm-ocr`（1.1B）或云端视觉模型 | — |

**为什么 embedding 选 512 维的小模型**：
- 它是**中文专用**的（我们的主战场是中文长文档）
- 512 维比 1024/1536 维**省一半以上内存和计算**，而在这个任务上精度差距不大
- 它能在 CPU 上跑——这保住了"克隆下来就能离线复现"这条底线

> 备选里还有 1024 维的 `multilingual-e5-large`——**如果语料是英文，
> 就该换它**。这也正是 MuSiQue 上得分低的原因（详见 4.4）。

## 6.2 Milvus 参数

| 项 | 值 | 说明 |
|---|---|---|
| 版本 | v2.5.14（standalone + etcd + MinIO）| |
| **索引类型** | **HNSW** | 图索引，查询快、召回高，适合低延迟 |
| **M** | **16** | 每个节点的最大连接数。越大召回越高，内存和建索引时间也越高 |
| **efConstruction** | **200** | 建图时的搜索宽度。越大图质量越好，建索引越慢 |
| **查询 ef** | **max(64, top_k × 4)** | **唯一能在查询时调的旋钮**，越大越准越慢 |
| **度量方式** | **COSINE**（余弦相似度）| 只关心方向不关心长度，文本场景的默认选择 |
| 集合命名 | `scout_<语料指纹+向量器身份的哈希>` | **换语料或换模型就是换集合** |

**集合名为什么要带哈希**：因为复用集合不会报错，
只会返回**属于旧语料/旧语义空间**的结果——这是最难排查的一类脏数据事故。

## 6.3 实测规模与两种后端对比

| 规模 | 集合实体数 | top-10 重合度 | 内存检索 p50 | Milvus 检索 p50 |
|---|---|---|---|---|
| 8 篇语料 | 156 | 100% | 15.7ms | 9.3ms |
| 40 篇语料 | 988 | 100% | 92.1ms | 21.5ms（快 4.3 倍）|

**"重合度"是什么**：内存那种做法是**精确**的（一个一个算），
Milvus 的 HNSW 是**近似**的（图搜索，可能漏）。
重合度 = 两者给出的 top-10 有多少是一样的。
**它其实就是"近似检索的召回损失"** —— 回答"为了这个速度，我们付出了多少准确度"。

> 在 988 个向量上重合度 100%，是因为**规模还太小**——
> 这个规模下近似检索几乎等价于精确检索。
> 要得出有意义的结论，得把规模拉到万级以上。

## 6.4 其他关键参数

| 项 | 值 |
|---|---|
| 分块 | L1 2400/400、L2 1600/200、L3 800/100（字/重叠）|
| 检索候选池 | `top_k × 4`（有界截断，控制重排延迟）|
| RRF 融合参数 | k=60 |
| 证据总预算 | 按字符数限制（防止超长上下文）|

# 第 7 层：怎么自己验一遍

所有命令**都不需要 API key**（离线替身实现）：

```bash
# 体检：当前哪些部件是真实模型，哪些还是离线替身
scout doctor

# 用内置小语料跑通一次问答
scout demo

# 在真实长文档语料上跑评测
scout eval run --dataset evals/longdoc_v1.json --corpus datasets/longdoc-gold

# 跑模块级消融（出那张"该改哪里"的排序表）
scout eval ablation --corpus datasets/longdoc-gold

# 核对向量库：与精确检索的重合度（= 近似召回损失）
scout milvus-smoke

# 看意图漏斗停在哪一层
scout intent

# 数据飞轮转一圈
scout flywheel --observations reports/observations.jsonl --list-only
```

**真实模型怎么开**：

```bash
set SCOUT_LLM_BASE_URL=<你的网关>
set SCOUT_LLM_API_KEY=<key>
set SCOUT_EMBED_BACKEND=local     # 启用语义向量模型
set SCOUT_MILVUS_ENABLED=1        # 启用 Milvus 后端
```

一键体检：`scout doctor` 会告诉你每一项现在是不是真的。

# 附：三句话总结

1. **它是个什么**：一个长文档问答系统，但它会判断"资料够不够"——
   不够就说不知道，而不是编一个。
2. **它凭什么可信**：每个模块都能单独关掉做消融（混合检索 −41.9pp、
   重排 −16.2pp、改写 −1.1pp），所以"哪里该改"是个排好序的数字而不是感觉；
   幻觉率和误拒率分开度量，所以"保守"和"笨"能分得清。
3. **它的边界在哪**：英文语料上表现差（向量模型是中文专用的）、
   小规模下近似检索的召回损失测不出来、拒答正确率的分母只有 2 条。
   **这些我都在报告里写清楚了，没有藏。**
