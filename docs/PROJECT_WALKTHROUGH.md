# scout 项目全景讲解

> **两份文档怎么用**：
> - **本篇**偏「为什么」——每个设计背后的取舍、我踩过的坑、可以讲的亮点。
> - **** 偏「是什么」——从零讲起、自顶向下、
>   含全部参数（模型/维度/索引）与**指标词典**（外行版）。
>   如果对方完全不懂 RAG，先给他看那份。

> 这份文档的目标是：**让你能用大白话把整个项目讲清楚**，包括每一层为什么这么设计、
> 为什么这么选型、以及每个结论是怎么测出来的。
> 不讲术语堆砌，讲"遇到了什么问题、想过什么办法、为什么最后选了这个"。

## 一、先讲清楚：这个系统到底在解决什么问题

### 从两个具体的失败场景说起

**场景 A：用户问了一个库里没有答案的问题。**

普通 RAG 系统的标准做法是：检索出最相关的几段文字，塞给大模型，让它据此回答。
问题在于——如果检索出来的东西其实答不了这个问题，大模型**不会说"我不知道"**，
它会用那几段不相关的文字，编一个听起来很合理的答案。

这类失败最危险的地方是：**它看起来很正常**。答案通顺、有模有样、格式也对，
只有去比对原文才发现是编的。用户如果不懂这个领域，根本看不出来。

**场景 B：用户问了一个需要跨两份文件才能答的问题。**

比如"对比一下 A 政策和 B 标准各自提出的 2027 目标"。
这需要同时找到 A 文件和 B 文件里的相关内容。
如果检索只返回了 A 的内容，大模型就会**只用 A 来回答**，
把 B 那部分也"顺理成章"地编出来。

### 所以这个系统的核心设计取向是：

> **宁可说"我不知道"，也不要编；并且"该拒答"和"不该拒答"要能被分开度量。**

这句话决定了整个系统长什么样。因为一旦你接受这个目标，你就必须回答两个问题：

1. 怎么判断"证据够不够"？（不能靠大模型自己感觉，它太自信了）
2. 怎么知道这个判断是准的？（拒答太多是"笨"，拒答太少是"编"，得能分别衡量）

后面所有的设计——数据层、检索层、门控、评测、运行时——都是围绕这两个问题展开的。

---

## 二、整体结构：三层，各管一件事

```
     ┌── 评测与自进化层 ──┐   负责"怎么知道它变好了"：打分、找失败、给改进建议
     ├── Runtime 运行层 ──┤   负责"调用怎么发生"：钱、延迟、状态
     └── 基础数据层 ──────┘   负责"语料长什么样"：解析、去重、版本
```

**为什么要分成三层？** 因为这三类问题的**排查方式完全不同**：

- 语料脏了 → 你不需要看检索代码，只要看数据层的报告
- 检索不准 → 你不需要怀疑模型，去看召回结果
- 回答变差 → 先分清是"检索没找到"还是"找到了但不敢答"

如果不分层，所有问题都糊在一起。指标掉了你只能靠猜。**分层最大的价值不是代码整洁，
而是让每个问题都有一个唯一的排查入口。**

## 三、数据层：为什么"脏数据比没数据更糟"

### 问题

真实的长文档（政策文件、年报、技术标准）转成文本之后，通常长这样：

- **双栏排版被读成一栏**：左右两栏的文字交错拼接在一起，句子读不通
- **跨页表格被页断成两张**：第二页的表少了表头，不知道那些数字是什么
- **同一份文件被导入多次**：库里躺着好几份一样的
- **公司年报的小节标题高度重复**：都是交易所强制模板，`公司基本情况` 出现几十次

### 为什么必须处理，而不是"差不多能用"

这里有个反直觉的点：**这些问题的表现不是"报错"，而是"所有下游指标一起变差"**。

比如双栏交错，它不会让程序崩，它会让检索到的段落读不通——于是
"检索命中率下降""回答质量下降""拒答率上升"全部一起出现。
你去查检索代码，代码没错；去换 embedding 模型，换了也没用。
**因为根因在几天前的一次文档导入里，而且它一声不吭。**

这就是"脏数据比没数据更糟"的含义：**没数据你会立刻发现，脏数据要排查很久。**

### 实际做了什么，效果多少

| 处理 | 实测效果（40 篇真实语料） |
|---|---|
| 双栏检测 + 阅读顺序重排 | **2 篇双栏文档重排了 660 行** |
| 跨页表格补写表头 | 在合成样本上验证（真实语料里跨页表格少） |
| 精确去重（内容哈希） | 丢掉 86 段 |
| 近似去重（SimHash） | 丢掉 29 段 |
| 合计 | **挡下 115 段重复，占 886 段的 13%** |

**那 13% 为什么重要？** 因为它们会占满检索结果的 Top-K。
用户看到的是"三条一样的结果"，而真正需要的第四条根本没进榜。

### 一个我特意做得"保守"的地方

我本来想加一道"阅读顺序质量门禁"：分数太低的文档直接拒收。
但在 40 篇真实语料上一跑，**5 篇被打了 0 分**——人工一看，它们没有任何版面错误，
只是**表格密集**：表格行本来就不以句号结尾，用"散文的规矩"去量表格，
低分反映的是体裁，不是错误。

**如果我当时就让它自动拒收，会静默丢掉 12% 的语料，而且报表上看起来一切正常。**

所以最后改成两条：
1. 指标只在"散文行足够多"时才下结论，否则返回"无法判断"（而不是"不合格"）
2. **默认不拒收**，只记录分数；要拒收必须显式设阈值——让"拦掉一些文档"成为有人签字的动作

改完之后，40 篇里**没有一篇被误判为低分**。

> **这件事的通用教训**：一个会误杀 12% 真实数据的指标，没有资格当自动门禁。
> 因为它的错误方式恰好是最难发现的——静默。

## 四、检索层：为什么是"混合检索 + 重排"

### 先讲两种检索各自的盲区

**稠密检索（向量）**：把问题和文档都变成一串数字，算"意思像不像"。
优点是能理解同义改写——你问"怎么退钱"，它能找到写着"退款流程"的段落。
缺点是**对精确词不敏感**：你问"标准号 GB/T 12345"，它可能给你一堆"标准"相关的内容。

**稀疏检索（BM25，就是关键词匹配的老办法）**：精确词很强。
但你问"怎么退钱"，它找不到写着"退款"的段落——字不一样。

**所以两个都用，然后把结果融合（RRF）**——各自找回自己擅长的那批候选，
再按"在几个榜单里都排前面"来排序。这叫混合检索。

### 然后加一层"重排"

混合检索会捞回一批候选（比如 16~32 条），但**排序还不够准**。
重排器的作用是：把这批候选逐条和问题放一起送进一个专门的模型，
重新打一遍分，挑出真正最相关的几条。

我们用的 cross-encoder（`bge-reranker`）——它比向量检索准，
因为它是把"问题和文档**一起**"看，而不是各自编码成向量再比。

### 关键：我是怎么确定"该优先改哪里"的

这里是我认为这个项目里最有价值的一件事：**我把每个模块都做成了可以单独关掉的，
然后在同一份语料上跑消融**，看每个模块去掉之后指标掉多少。

| 关掉哪个模块 | MRR 变化 | 结论 |
|---|---|---|
| 混合检索（只用稠密） | **−41.9pp** | 最大杠杆 |
| 重排 | **−16.2pp** | 第二 |
| 查询改写 | **−1.1pp** | **几乎无效** |
| 父块合并换 REPLACE 策略 | **+6.8pp** | **反直觉：反而更好** |

**为什么这件事比单个指标重要？**

因为它把"该先改什么"变成了一个**排好序的数字**。
−41.9pp 和 −1.1pp 是完全不同的量级——一个是"不做就残废"，一个是"做了也白做"。
如果没有这个排序，你调参就只能靠感觉。

那 +6.8pp 是什么？主流的做法是"命中子块就把父块**展开**进来"（获得更多上下文），
但我实测发现**用父块替换子块**反而更好——因为展开会引入大量无关内容，
把重排的候选池冲淡了。**这是一个与直觉相反的结论，我也是测了才知道。**

### 公开基准上的重排消融（300 条配对比较）

在这份语料之外，我在 MuSiQue-Ans 公开基准上做了同一件事：

| 重排器 | Recall@5 | Recall@10 |
|---|---|---|
| 词法重排（基线） | 26.8% | 36.7% |
| cross-encoder | 38.5% | 41.0% |
| **配对差量** | **+11.67pp**，置信区间 [8.83, 14.67] | +4.33pp [2.50, 6.50] |

**几个设计上的讲究：**

- **配对比较**：不是拿两组各自求平均再相减，而是**每条样本先算出差量再统计**。
  这样"这题难不难"这个共同因素被消掉了，比两组独立均值灵敏得多。
- **置信区间不跨零**才算结论成立。跨零的数字不能拿去汇报。
- **300 条**而不是 50 条：早期我用 50 条测过，得到 48%，看起来很漂亮。
  扩到 300 条变成 38.5%。**我把"前缀难度曲线"也算了出来**——
  前 50 条确实比全集容易（46% vs 38.5%），所以那个 48% 不是假的，但它不具代表性。
  **报绝对指标必须用它自己样本量对应的那一行。**

## 五、门控：这个项目最有特色的部分

### 问题的本质

前面说检索能找到正确答案。但**找到证据 ≠ 该回答**。

这两件事之间有一道判断题：**这些证据够不够支撑一个回答？**
这道题不能让大模型自己答——它太自信了，永远觉得"差不多可以答"。

所以我们用一个独立的评估步骤（也会调模型，但问的是不同的问题）：
给它问题和证据，让它评四项——相关性、覆盖度、能不能答、问题本身有没有歧义，
然后给一个路由决定：直接作答 / 改写查询再检索 / 向用户澄清 / 确实没有资料。

### 幻觉率和误拒率是**两个指标**

这是我觉得最关键的一个设计决定。

如果只看"拒答率"，你无法判断系统是**保守**还是**笨**：
拒答率 70% 既可能是"它很谨慎，只答有把握的"，也可能是"它什么都不会，全在推"。

所以我们把它拆成两个：

- **幻觉率**：本该拒答的题，它却答了（编）
- **误拒率**：本可以答的题，它却拒了（怂）

这两个指标会**互相拉扯**：把门槛调高，幻觉率降、误拒率升；调低则反之。
分开度量之后，你才能说"我现在是在哪个位置，要不要往哪边挪"。

### 两套语料的对照——让"拒答率高"变成可解释的数字

单看一个数字很危险。比如在 MuSiQue 基准上，我们的作答率只有 24%——
听起来是不是"太保守了""系统很笨"？

但我们同时在**中文长文档语料**上测过：**作答率 68.4%、误拒率 0%**。

**同一套门控、同一个阈值**，一个 24% 一个 68%——差别不在系统的性格，
而在**语料与语言**：MuSiQue 是英文语料，而我们当时用的向量模型是**中文专用**的
（`bge-small-zh`）。语言不匹配 → 检索质量差 → 证据不足 → 拒答。

我专门验证过这个解释：把向量模型换成中文语义模型，纯稠密通道的命中率
从 9.7% 掉到 6.8%——**不升反降**，正好说明中文模型编码英文段落发挥不出语义优势。

> 所以"作答率 24%"的正确读法是：
> **在语料与模型语言错配的条件下，门控只在 24% 的问题上认为证据充分。**
> 这不是保守，这是它对证据质量的如实反映。

## 六、评测：为什么这么设计

### 四层指标，而不是一个总分

| 层 | 回答什么问题 | 例子 |
|---|---|---|
| 检索层 | 找对东西了吗 | Recall@5、MRR |
| 生成层 | 答得对不对 | 关键词覆盖、归因支撑率 |
| 安全层 | 该拒的拒了吗 | 幻觉率、误拒率、注入泄漏率 |
| 轨迹层 | 过程健康吗 | 平均步数、工具失败率、预算终止率 |

**为什么要四层？** 因为"总分掉了"是一个没有信息量的结论。
四层之后你能立刻定位：是检索退化了，还是检索没变但生成变差了，还是门控变激进了。

### 为什么必须有"消融"

因为**模块之间会互相掩盖**。

举个真实例子：查询改写单独看几乎没有贡献（−1.1pp），
但如果检索本身很差，改写有时能救回来几题，看起来就"有用"了。
只有把模块单独关掉、在同一份语料上跑，才能看出它的**边际贡献**。

**消融的设计原则是：每次只改一个维度。** 这样指标差异才能归因到那个维度上。
所以消融矩阵里每一行都只动一个开关。

### 为什么要有公开基准（而不只是自建语料）

自建语料的问题是：**它是我自己造的，我可能无意中把它造得适合我的系统**。
这是一个自己给自己出题的风险。

所以额外跑一个公开基准（MuSiQue-Ans，别人造的、有标准答案的多跳问答集）。
它的作用不是"证明我很强"，而是**提供一个我不可能作弊的对照**。

有意思的是，它暴露的问题最多——因为它不受我的控制。

### 为什么要置信区间

50 条样本算出来的 48% 和 300 条算出来的 38.5%，哪个更可信？
直觉上都会说后者，但**直觉说不清差多少**。

所以用 bootstrap 重采样算 95% 置信区间：
300 条时是 [35.0, 42.2]（±3.6pp），50 条时是 [39.0, 57.0]（**±9pp**）。

**区间宽度本身就是"这个样本量能支撑多强的结论"的度量。**
拿一个 ±9pp 的数字去宣布"我们提升了 5 个百分点"，是没有意义的。

## 七、Runtime 运行层：钱、延迟、状态

这一层解决的问题很直白：**调用怎么发生、状态放哪、钱怎么不超**。
它的设计原则是"**策略与业务分离**"——所有部件都是包装器，对上完全同形。

### 装配顺序不是随意的

```
  缓存（最外） → 预算（中间） → 路由（最内） → 真实模型
```

**为什么这么排？**

- **缓存在最外**：缓存命中不花钱。如果预算在缓存外面，
  一次"本来免费"的命中会先被预算拦下——用户看到"预算不足"，而这次调用根本不需要钱。
- **路由在最内**：预算需要知道"这次要花多少钱"，而花多少钱取决于用哪个模型。
  先路由再判预算，才能用对的价格判断。

`scout stack` 命令会现场演示这件事：第一次调用花 562 token，**第二次 0 token**
（缓存命中，而且没触发任何预算检查）。

### 语义缓存的"作用域"是关键

同一个问题，在**不同证据**下要给出不同答案。

"这份年报的营收是多少"——换了知识库版本之后，问题一字没变，但答案必须变。
所以缓存项带一个 **scope（作用域）**：任务类型 + 证据指纹 + 模型版本。
**scope 变了就是 miss，哪怕问题一模一样。**

只按问题文本缓存，是这类实现最常见的严重错误：它会把**旧答案喂给新数据**。

### 模型路由

Agent 的调用里，大量是低难度的结构化判断（分类、打分、改写），
用旗舰模型做是纯浪费。所以按任务名分档：
轻任务走快模型，重任务走旗舰模型。

**但白名单而不是黑名单**——拿不准就走强模型。
路由错了多花钱，比路由错了降质量更容易接受。

## 八、可恢复运行时：中断、审批、时间旅行

### 为什么状态必须外置

进程随时可能被重启、扩缩容。如果状态在内存里，重启就没了。

**而在"等人审批"的场景下，这不只是"丢状态"——是会话永久卡死。**
用户看到的是"等待审批"，如果这时进程重启而状态丢了，那次审批永远等不到结果。

所以有三种可替换的存储后端：内存（演示）、文件 JSONL（本地可恢复）、
**Redis（多副本、跨进程）**。三者的**存储形态一致**（都是 append-only），
所以换后端不换语义。

### 副作用为什么不能重放

这是我认为最有意思的一个设计点。

Agent 在执行过程中调了一个"发邮件"的工具，然后下一步触发了人工审批，
审批通过后从断点恢复——**恢复时那封邮件不能再发一次**。

做法是：副作用按"调用槽位（第几步调的哪个工具）+ 血缘"记账，
重放时命中的是**已完成的副作用**，直接返回缓存结果，不重复执行。

审批超时默认 **拒绝**（fail-closed）：宁可这次操作没做，也不默认放行。

### 时间旅行

因为检查点是 append-only 的，所以可以"回到第 3 步分叉"，
用当时的完整状态重新往下走。这对调试 Agent 很有用——
出问题时能回到那个决策点，换一种走法看会发生什么。

## 九、数据飞轮：让系统自己找自己的问题

### 思路

线上每次问答都会留下结构化记录（问题、结果、检索到了什么、支撑率多少）。
这些记录本身就是"系统在哪里失败"的证据。

飞轮做四件事：

1. **采集**：把观测落盘（append-only JSONL）
2. **挖掘**：从里面挑出"值得进评测集"的样本——拒答的、重生成过的、支撑率低的
3. **复核**：**必须人工过一遍**（这一步不能省）
4. **回归**：新样本进评测集，重跑，看改动是不是真的更好

### 为什么"复核"这一步不能自动化

因为模型判错的样本里，混着**"这题本来就不该答"**（库里确实没有）。
如果你把它当成"应该答对"的样本加进评测集，
**你就是在系统性地惩罚一个行为正确的系统**——门控会被越调越松，
最后变成一个自信胡说八道的系统。

所以自动挖掘只产出**候选**，入库必须经过显式判断。

### 实测这一圈跑通了什么

```
观测 120 条（按问题去重后 90 个）
其中拒答 18 条 → 挖出候选 18 条 → 复核通过 18 条
评测集：19 → 37
```

**跑的过程中暴露了两个 bug，都是"单测里两个模块各自都对、接起来就错"的那种：**

1. **字段名错配**：挖掘器读 `retrieved`，观测写的是 `retrieved_sources`。
   取值全为 None → 检索数量当 0 → 每条观测都被判成"空检索"跳过 →
   **飞轮转一圈挖出 0 条候选，而报告上一切正常。**
2. **`error_code` 被当成异常信号**：在这套代码里 `error_code` 是"类型化结果"的标识
   （拒答本身就带），把它当异常判 → **所有拒答都被误判成崩溃**。

这两个都是端到端跑才暴露的。所以我加了一条契约测试：
**用真实管线产出的记录去喂挖掘器**，它必须读得懂。

## 十、多模态入口：让图片也能走同一条路

### 关键的设计取舍：不是新开一条链路

加图片支持的时候，最容易的做法是"新写一个图片处理流程"。但我选了另一种：

**抽取器把图片变成文本之后，直接进原来那条流水线**——
版面还原、切分、去重、版本登记，一行都没改。

**为什么这么选？** 因为"多模态"不该是一条平行链路，而是**入库入口多了一种输入形态**。
如果新开一条，你会发现切分规则、去重规则、版本规则全都要维护两份，
而且迟早会漂移。

### OCR 的选型：三条路都试了

| 方案 | 成本 | 速度 | 表头准确率 |
|---|---|---|---|
| 云端通用推理 VLM（kimi-k3） | 3.5k~12k token/张，波动 3.4 倍 | 67~270 秒 | ✅ 对 |
| 本地专用 OCR（glm-ocr，1.1B） | **零**（本地推理） | **4~25 秒** | ❌ 错 |
| 智谱 MaaS（同一模型，走 API） | 0.2 元/百万 token（约 1 元/2000 张） | 1.5 秒 | 未测（无 key） |

**这里有一个我自己踩出来的重要教训。**

一开始我的评价指标只有 18 项，**全是"单元格里的值"**（容器名、镜像名、端口）。
结果两个模型都是 18/18，我据此写下"质量持平"。

**直到端到端验证时才发现不对**：图片入库后**检索能召回（4/4），但门控拒答了**。
深挖下去才看到——**表头**：

| | 表头 |
|---|---|
| 原图真实值 | `Name / Container ID / Image / Port(s) / CPU % / Last started` |
| 本地 glm-ocr | `ID / Name / - / - / - / 0% / 3 months ago` ← **错** |
| 云端 kimi-k3 | 与真实值一致 ← 对 |

**数据单元格两者都对，但表头只有大模型读得出。**

**表头为什么是决定性的，而不是装饰**：它是**检索与门控的语义锚点**。
问"端口映射是什么"要靠 `Port(s)` 这个字面锚点才能匹配上；
表头错了或缺了，覆盖度就上不去，系统就会**拒答一个它其实已经召回正确答案的问题**。

把表头补进 ground truth（18 → 23 项）后重测：**本地模型 17/23（74%）**。

> **这条教训比任何性能数字都值钱：**
> 一个只检查"值"的指标，会让所有模型看起来一样好——
> 直到你在真实链路上发现系统在拒答。

### 顺带做的两个性能优化

**一、让它自己停。**

本地模型每次都写满输出上限才停（`done_reason` 全是 `length`），
然后写出几百行重复的垃圾。我没有直接砍上限——因为**砍上限会让长文档被截断，
而截断的表现是"表格缺行"，比变慢严重得多。**

而是配了一个停止序列（`stop=["</table>"]`）：识别到表格闭合就停。
效果：**耗时 21.8 秒 → 4.2 秒（快 5 倍），生成量 4096 → 688 token，
而且不再需要事后清理。**

（这个小优化有个副作用要处理：接口命中停止序列时会**把它从输出里删掉**，
所以 HTML 缺个闭合标签，得补回来。判据是"结构未闭合"而不是"字符串没出现过"——
后者恒为假，这个错我犯过、靠跑一次才看出来。）

**二、端点的上下文上限会静默毁掉输出。**

本地推理的兼容接口在不显式指定上下文长度时，输出被硬限在 4096。
后果有两种：表格被**截断在中间**，或者更隐蔽的——**撞上限后开始复读**。
而这两种情况下，我的关键词命中率**仍然是 18/18**（它只查关键词在不在，
发现不了"尾巴是垃圾"）。

修法是用原生接口（能显式指定上下文），再加一步"尾部退化裁剪"：
从末尾往前找"同一行重复 ≥5 次"的连续段裁掉。
判据只看尾部重复、不假设文档结构，所以"表格后面还有正文"的文档不会被误伤。

## 十一、我做错的几个判断（这部分也许最有信息量）

我把这些列出来，因为**它们比成功的地方更能说明工程是怎么做的**。

1. **差点得出完全相反的结论**：第一次探测云端模型支不支持图像时，
   我给的输出预算太小，被"思考过程"吃光了，返回的内容是空的。
   我据此写下"它不支持图像"。**后来把原始响应 dump 出来，才看到思考过程里
   明明白白写着"图里是 7391"——它看得见，而且读对了。**
   教训：结论要基于原始数据，不能基于封装后的字段。

2. **扫 num_predict 差点把正确性换成速度**：看到模型总写满上限，
   第一反应是"砍一半"。但我先扫了一遍拐点，发现**所有配置都撞上限**——
   这说明预算是"上限"而不是"浪费"，砍它会让长文档截断。

3. **降采样到底值不值，两种工具方向相反**：在云端模型上，降采样让输入 token 降了 37%，
   但总成本反而涨了 2.4~3.5 倍（因为"思考长度"波动 6 倍，把输入那点节省淹没了）；
   在本地专用 OCR 上，降采样让耗时降了 19%（没有思考开销，输入变小就线性地省）。
   **同一个优化，在不同工具上是相反的结论。**

4. **一个"会误杀 12% 数据"的指标差点被我设成自动门禁**（见第三节）。

5. **报告里写过一句没有数据支持的解读**：我凭直觉写了"小语料下内存检索更快"，
   结果实测在 156 个向量时本地向量库就已经更快（9.3ms vs 15.7ms）。
   原因是我们的内存实现是纯 Python 逐条算余弦，瓶颈在解释器开销，
   一次网络往返（几毫秒）相对它可以忽略。**已改成由数据算结论。**

## 十二、面试怎么讲（60 秒版）

> 「这是一个长文档问答系统，我给它定的核心目标是——**宁可说不知道，也不要编**。
>
> 为了做到这一点，我把问题拆成了两块：
>
> **第一块是判断"证据够不够"。** 这件事不能交给大模型自己，它太自信了。
> 所以我用独立的评估步骤做这个判断，然后把**幻觉率和误拒率分开度量**——
> 因为只看拒答率，你分不清系统是谨慎还是笨。
>
> **第二块是让每个模块的效果可以被量出来。** 我把所有模块都做成能单独开关的，
> 在同一份语料上跑消融。结果是：混合检索贡献 41.9 个点的 MRR、重排 16.2 个点、
> 而查询改写只有 1.1 个点——**这个排序告诉我该往哪里投时间。**
>
> 这两件事合起来，让"系统好不好"从感觉变成了数字。
>
> 比如有一次我在公开基准上把样本从 50 条扩到 300 条，
> 发现以前报的 48% 变成了 38.5%——**因为前 50 条恰好更容易**。
> 这个数字我本来可以不测、不报。但我把它写进了报告，
> 还画了「前缀难度曲线」。
>
> 我觉得这件事比任何一个指标都重要：**你知道你的数字是怎么来的、边界在哪。**」
