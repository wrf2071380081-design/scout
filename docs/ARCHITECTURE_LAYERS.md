# scout 三层架构：数据层 / 运行层 / 评测自进化层

> 这份文档回答两个问题：**这套系统由哪三层组成**，
> 以及**每一层各自对标当下的哪类前沿工作**。
> 判断标准只有一条：每层都要能说出"我为什么独立存在、以及不做我会坏在哪"。

---

## 0. 一页总览

```
┌──────────────────────────── 评测与自进化层 (scout.evolution) ───────────────────────────┐
│  LLMJudge（语义评分 + 位置/长度去偏）  FailureMiner→ReviewQueue（数据飞轮）  ParamTuner   │
│  产出：分数、候选评测样本、参数建议        纪律：只增不减 / 不自动应用 / 留痕可回滚        │
└───────────────────────────────────────────┬────────────────────────────────────────────┘
                                            │ 用指标驱动改进
┌──────────────────────────── Runtime 运行层 (scout.runtime) ────────────────────────────┐
│  IntentFunnel（规则→语义→LLM）  SemanticCache（作用域隔离）  ModelRouter（成本杠杆）      │
│  BudgetedLLM（预扣+硬上限+结算）  token 流式  CheckpointStore（内存/文件/Redis）          │
│  纪律：策略与业务分离 / 决策留痕 / 降级显式且清晰                                        │
└───────────────────────────────────────────┬────────────────────────────────────────────┘
                                            │ 拿到干净、可检索、可追溯的语料
┌──────────────────────────── 基础数据层 (scout.data) ───────────────────────────────────┐
│  版面还原（双栏/跨页表格）  两段去重（内容哈希 + SimHash）  版本与血缘（doc_id+version）  │
│  纪律：坏数据比没数据更糟 —— 入库前有质量门禁，丢弃可追溯                                │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

三层之间的**方向是单向的**：数据层产出语料，运行层消费语料并产生痕迹，
评测层消费痕迹并反向驱动前两层的参数与结构。
反向只有"驱动"、没有"直接改"——这是刻意的，见第 4 节。

---

## 1. 基础数据层（`scout.data`）

### 它为什么必须独立存在

上游是脏的（PDF 双栏、跨页表格、重复导入、持续更新），
下游是挑剔的（检索要求每条证据能追到来源与版本）。
把这段塞进"读文件"里，会得到一个没人敢改的函数，而且**语料问题会伪装成模型问题**：
召回率低你以为是 embedding 不行，其实是分栏时左右两栏的文字被交错拼接了。

### 四个部件与它们各自的可验证断言

| 部件 | 解决什么 | 怎么证明它有用 |
|---|---|---|
| `layout.restore_layout` | 双栏被读成一栏、跨页表格被页断成两张 | 合成双栏文本上，重排后左栏整列在前；跨页表在续页补写表头 |
| `layout.reading_order_ratio` | 入库前的质量哨兵 | 连贯文本的比值高于错序文本；低于阈值直接拒收 |
| `dedup.deduplicate` | 同一条内容占满 Top-K | 改 1 个字的近重复被 SimHash 拦下（汉明距离 ≤3），不相干的文本不被误杀 |
| `dedup.VersionRegistry` | 文档更新后的缓存脏读 | 缓存键含 `doc_id + 内容指纹 + 模型版本`，三者任一变化即失效 |

### 两个刻意的设计决定

1. **先精确去重、再近似去重。** 精确去重是 O(1) 且零误判，先把完全一样的干掉能显著减少
   近似扫描量。便宜且确定的检查永远放前面。
2. **坏数据入库前拦掉，而不是入库后再修。** 语料质量是隐性变量，
   它不会报错、只会让所有下游指标一起变差，且无法归因。
   所以 `ingest` 有质量门禁（`min_reading_order`），被拒的文档进报告。

**不使用版面分析大模型**（LayoutLM / Docling 那一路）是清醒的取舍：
启发式能覆盖"双栏 + 跨页表格"这两个最高频的破坏性场景，
且零依赖、可离线复现、行为可解释；复杂版式（印章、公式、图文混排）应当明确交出去，
而不是把启发式堆得更复杂。

## 2. Runtime 运行层（`scout.runtime`）

### 它为什么必须独立存在

运行时的三类问题——**钱、延迟、状态**——都不属于业务逻辑，
但都会在业务逻辑里到处漏出来（每个函数都判断一下预算、都看一眼缓存）。
`scout.runtime` 把它们全部收进包装器：所有部件都实现同一个
`complete(request) -> LLMResponse`，对上完全同形。
**业务代码不知道今天有没有开路由**，这让策略可以随时开关、做对照。

### 五个部件

| 部件 | 解决什么 | 关键设计点 |
|---|---|---|
| `IntentFunnel` | 分类该走规则还是模型 | **不取 argmax**：双高且分差够大才自动路由，否则澄清。高敏感意图即便高置信也强制确认 |
| `SemanticCache` | 重复问题不再花钱 | **作用域隔离**：`scope = 任务 + 证据指纹 + 模型版本`。同一问题换知识库必须 miss |
| `ModelRouter` | 成本最大的一根杠杆 | **白名单**而非黑名单：拿不准就走强模型；每次决策进 `decisions` 可审计 |
| `BudgetedLLM` | 任务把账单烧穿 | **预扣 + 硬上限 + 结算**：调用前查预算，不足即类型化拒绝（不是跑完才透支） |
| `stream.iter_tokens` | 首 token 延迟 | 统一取词接口：有流式用流式，没有就退化；观察者钩子抛异常不影响生成 |

### 三条硬约束（这一层的"宪法"）

1. **决策必须留痕。** 路由决策、缓存命中、预算冻结都落结构化记录。
   没有留痕的优化既无法证明自己有效，也无法在出问题时被摘除。
2. **降级要显式且清晰。** 没有向量器 → 退化为精确匹配并**如实说明**（不假装语义命中）；
   没有流式能力 → 一次性返回（而非报错）；没配 Redis → 由调用方显式选文件或内存后端。
3. **语义不同的策略不该长得一样。** `complete` 会自动重试，`complete_stream` **不重试**——
   流式已经吐出去的内容收不回来，重试会造成重复输出。
   **同名的"重试"在两个方法里语义不同，就必须有不同的实现。**

### 状态存储：为什么外置是硬要求

`InMemoryCheckpointStore` / `FileCheckpointStore` / `RedisCheckpointStore` 三者同接口。
Redis 版的存在理由不是"更快"，而是：进程随时会被调度重启、多副本要共享同一份会话状态，
而 HITL 场景里用户正看着"等待审批"——这时状态丢了，那次审批永远等不到结果。
**代价是多一跳网络往返；收益是会话不会永久卡死。** 这笔账不需要犹豫。

## 3. 评测与自进化层（`scout.evolution`）

### 它和 `scout.evaluation` 的分工

- `scout.evaluation`（已有）：**测量仪器**。给定数据集与配置 → 指标 → 报告。
- `scout.evolution`（本层）：**用测出来的东西改进系统**。三个部件对应三个改进路径。

### 三个部件

| 部件 | 改进路径 | 关键纪律 |
|---|---|---|
| `LLMJudge` | 词法指标测不出"有没有编造"时，用模型做语义评分 | 位置偏见 → 双跑换序取平均；长度偏见 → 写进 rubric；自我偏好 → 记录裁判模型，禁止同源自评 |
| `FailureMiner`+`ReviewQueue` | 线上失败 → 评测集增量（数据飞轮） | 自动挖掘**只产出候选**；入库必须显式批准；按问题文本去重（同一难题不重复计数） |
| `ParamTuner` | 指标结构 → 参数建议 | 缺失指标不等于 0；效应量小于噪声带不建议改动；样本不足禁止自动应用 |

### 这一层唯一不可妥协的纪律

> **所有自动变更都要有留痕与回滚路径。**

具体落地为三个闸门：

1. **裁判要校准**：`JudgeCalibration` 用人工锚点算偏差与一致率，
   样本 < 10 条或一致率 < 0.7 一律标记为"不可作为决策依据"。
2. **样本要复核**：模型判错的样本里混着"这题本来就不该答"。
   直接加进评测集会系统性惩罚一个**行为正确**的系统——
   门控会被越调越松，最后变成自信胡说八道。
3. **参数要证据**：`ParamSuggestion.auto_applicable` 只有在
   `样本量 ≥ 200` 且 `置信度 ≥ 0.7` 时才为 True，其余一律人工确认。

**为什么这么保守：** 单次评测通常只有几十到几百条样本，这个量级上 1~2pp 的差异
完全可能是噪声。自动应用噪声，系统会来回震荡，
而且每次震荡都会被"新数据"重新合理化——**自进化系统一旦开始自我合理化，
它坏得比手动系统更彻底。**

### 一个容易被忽视的设计：矛盾建议不自动生效

误拒率高时会建议**下调**充分性门槛，幻觉率高时会建议**上调**——方向相反。
两条都带 `auto_applicable` 时它们不可能同时为真（同一参数两个方向），
实现上后写的会覆盖先写的，最终由 `suggestions.sort` 的置信度决定谁在前面。
**互相矛盾的自动变更必须由人裁决**，这一点写在了 `ParamTuner` 的注释里。

## 4. 三层如何协同：一次问答的完整生命周期

```
① 文档进来    data.restore_layout → 质量门禁 → 结构切分 → 两段去重 → 版本登记
                                    │
② 问题进来    runtime.IntentFunnel ├─ 规则命中 → 直接路由
                                    ├─ 语义双高 → 自动路由
                                    └─ 歧义/低置信 → 澄清或 LLM
                                    │
③ 调用发生    runtime.ModelRouter 决定用哪个模型
              runtime.SemanticCache 先查缓存（scope 含证据指纹）
              runtime.BudgetedLLM   每次调用前查预算
              runtime.stream        需要时逐 token 吐给前端
                                    │
④ 痕迹留下    trace（阶段/决策/用量）→ 结构化存储
                                    │
⑤ 改进发生    evolution.FailureMiner 挖候选 → ReviewQueue 复核 → 评测集增量
              evolution.ParamTuner   按指标结构给建议（不自动应用）
              evolution.LLMJudge     给词法指标补上语义评分（去偏后）
```

**关键点：⑤ 不能直接改 ①②③。** 它只能通过"建议 → 人确认 → 改配置"这条链路生效。
这条约束牺牲了自动化程度，换来的是**每一次变更都可归因**。
在这个系统里，"为什么这个阈值是 0.45"永远有答案——这比"它自己学会了 0.45"重要得多。

## 5. 与前沿方向的对应关系

把 scout 的每一层对着当下公开讨论较多的几个方向看，
**每条都标注了"我们是真做了"还是"只是知道"**——不做过度声称。

| 前沿方向 | 对应本项目的什么 | 做到什么程度 |
|---|---|---|
| **Agent Harness / 执行框架** | `scout.agent`（ReAct 循环）+ MCP server + 工具注册表 + 沙箱 | 真做了：循环、工具契约、危险工具审批、stdio MCP |
| **Durable Execution / 可恢复运行时** | `scout.hitl`（checkpoint + 副作用账本 + 时间旅行）+ 三种 CheckpointStore | 真做了：跨进程恢复、节点幂等、Redis 外置状态 |
| **Context Engineering** | 三级父子分块、证据压缩、观测压缩、静态/动态提示词切分 | 真做了：压缩有多档预算参数 |
| **Cost-aware Serving** | `ModelRouter` + `SemanticCache` + `BudgetedLLM` | 真做了：三元组（路由/缓存/预算）+ 决策留痕 |
| **Evals as a Product** | `scout.evaluation`（四层指标 + 消融 + 公开基准 + CI） | 真做了：置信区间、配对消融、负向结论 |
| **Data Flywheel / 自进化** | `scout.evolution`（挖掘 → 复核 → 回归 → 参数建议） | 真做了：完整链路 + 三道闸门；**未做自动微调**（数据量不够，硬上就是过拟合噪声） |
| **Multi-Agent** | `scout.multiagent`（Supervisor + 扇出 + 失败隔离 + 结论回传） | 真做了：上下文隔离、失败不传染、覆盖缺口如实上报 |
| **数据治理 / Lineage** | `scout.data`（版面还原 + 去重 + 版本血缘 + 缓存键） | 真做了：入库门禁、丢弃可追溯 |
| **Prompt / 参数自动优化** | 仅 `ParamTuner` 给建议 | **只做到"建议 + 证据"**，没做自动搜索——样本量不支持，做了也是噪声 |

**诚实标注的三条"没做"：**
1. 没做自动微调（SFT/DPO）——偏好对的量级还差两三个数量级；
2. 没做分布式预算（Redis 原子预扣 + 结算流水）——本地版语义已通，缺的是生产验证；
3. 没做多租户隔离——接口层留了位置，没做过真实压测。

## 6. 如果继续往前走，优先级是什么

按"能带来证据增量"而不是"听起来先进"排序：

1. **让飞轮真正转起来**（现在链路通了但没有真实线上痕迹喂它）：
   把 `FailureMiner` 接上真实的 trace 存储，跑通一次"挖掘 → 复核 → 评测集增量 → 回归"。
   **价值在于它是唯一能让其他所有指标持续改善的机制。**
2. **预算分布式化**：`BudgetedLLM` → Redis 原子预扣 + 结算流水落库 + 幂等键。
   这是"单机实现"与"生产可用"之间最明显的那道缝。
3. **Harness 侧的验证闭环**：目前 Agent 循环有工具与沙箱，但缺少
   "改完跑测试 → 失败就回滚"的自动验证回路。这是 Code Agent 类产品最核心的能力。
4. **裁判校准**：补一批人工锚点把 `JudgeCalibration` 填满，
   让 LLM 评分从"参考"升级为"可采信"。
